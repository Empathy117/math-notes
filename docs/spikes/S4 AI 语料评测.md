# S4 实测：AI 语料评测（DeepSeek flash）

日期：2026-09-26。模型：`deepseek-flash`，DeepSeek 官方接口（`/models` 只列出 `deepseek-flash` 与 `deepseek-v4-pro`；旧 ID `deepseek-chat`、`deepseek-reasoner`、`deepseek-v4-flash` 实际都由 `deepseek-flash` 应答）。

- 代码：`packages/core/src/ai/`，包括提示词、结果解析、重试、宿主语义检查、DeepSeek 适配器。
- 评测器：`spikes/s4-ai-corpus/run.ts` 与 `judge.ts`。
- 语料：
  - 开发集：`corpus.json`（80 条生成）、`edit-corpus.json`（17 条改写），提示词是对着它调的。
  - 留出集：`heldout.json`（64 条生成）、`heldout-edit.json`（11 条改写），只用来验证，不拿来调提示词。
- 原始结果：`spikes/s4-ai-corpus/results/`。

评测一共做了三轮：
1. 用原来的 50 条语料找出问题。
2. 修复这些问题，把开发集扩到 97 条。
3. 新写一套留出集，修复前两轮留下的问题，再用留出集验证修复能推广到没见过的输入。

## 结论

**deepseek-flash 在非推理模式下满足 S4 的全部指标。** 最终配置在两套语料上各跑三轮，全部通过。

| 指标 | 开发集（三轮） | 留出集（三轮） |
|---|---|---|
| 通过 | 97/97 ×3 | 75/75 ×3 |
| 生成准确率 | 68/68 | 58/58 |
| 歧义暴露率 | 10/10 | 17/17 |
| 歧义主解释一致 | 10/10、9/10、10/10 | 17/17、16/17、16/17 |
| 误报歧义 | 1/58（有意为之，见第 21 条） | 0/41 |
| 越界识别 / 误拒 | 3/3、0/68 | 4/4、0/58 |
| 重试提示词 | 6/6 | 2/2 |
| 选区改写（D8） | 17/17 | 11/11 |
| 首轮触发重试 | 0/74 | 0/62 |
| 完整结果延迟 p50 / p95 | 818 / 1171 ms | 829 / 1184 ms |

前提与决定：
- 适配器显式关闭思考（`thinking: {type: "disabled"}`），`max_tokens` 默认值 1200。
- `alternatives` 只放含义不同的读法，同一含义的其他写法放在 `notations`。
- 同步门会重问一次：KaTeX 拒绝，或输出不可用（截断、JSON 损坏）时触发。
- 解析层会修补模型常犯的 JSON 小错，绝不把坏 JSON 当公式插入。
- 两类模型标不稳的歧义由宿主确定性地补上另一种读法：手敲的 `sinx/x`，和口述的"根号下 A 加 B"。
- 化学式、带单位的数值不算越界，用原生写法输出。

遗留问题见文末。

## 第三轮：留出集与再修复

### 做法

第二轮的提示词是对着开发集的 80 条调出来的，在开发集上再调下去，分数只会越来越好看，说明不了能否推广。所以这一轮按下面的顺序做：

1. 先写留出集：同类歧义换一种表面形式，外加不该标歧义的对照题、长尾记号、复杂长公式。
2. 用当时的提示词跑出基线。
3. 按**开发集**的失败修改。
4. 在留出集上验证。

在留出集上发现的问题（化学式和单位误拒、siunitx、改写指令不清）修好之后，那几条就不能再拿来当验证了。所以针对这几处修改，另写了新用例（`ho-boundary`、`ho-fresh`）来验证，这些新用例也从没拿来调过提示词。

### 留出集基线

用第二轮定稿的提示词，三轮结果：
- 47/47 全过，误报歧义 0/25。
- 歧义暴露 10–11/14。没暴露的：`lim x->0 tanx/x`（三轮都没有）、`e^(sinx/x)`（两轮没有）、`根号下2x减1`（三轮都没有）。
- 主解释一致 13/14：`e to the x plus one` 以 e^{x+1} 为主解释。

另外两类用例的基线：
- 化学式和单位（`ho-natural`，5 条）：**3–4 条被误拒**。`硫酸的化学式`、`氢氧化钠和盐酸反应的化学方程式` 答 unsupported（mhchem），`25 摄氏度` 答 unsupported（siunitx）。
- 复杂长公式（`ho-complex`，5 条）：全部一次通过，但傅里叶级数那条用了 329 个 token，逼近当时 500 的上限。

### 改了什么

| 改动 | 依据 |
|---|---|
| 规则 4 分条细化：不带"下"的"根号 2 加 1"只管紧跟的一项；"three over y minus two"取 \frac{3}{y}-2；手敲的 `函数名 x/x` 外面套了 lim、积分、求和等结构时同样标歧义 | 开发集 sc-03、sc-07、sl-01 |
| 加一条外层是积分的歧义 few-shot `int_1^2 cos t/t dt`，两套测试里都没有积分外层 | 开发集 sl-01 |
| 规则 7、8、11：化学式、化学方程式、带单位的数值用原生写法输出，不算越界；mhchem 的 `\ce` 和 physics 的命令一样改写；只有点名要 siunitx 才判越界 | 留出集误拒，用 `ho-boundary` 的 8 条新用例验证 |
| 规则 8 写明 siunitx 例外 | 3a 版里 `用 siunitx 写 5 千克` 三轮中有两轮没判越界，用 `ho-fresh` 验证 |
| 改写提示词：只说了"这个""改一下"、没说改成什么的，算指令不清，不要猜 | 3a 版里"这个"有一轮被模型猜着改了，用 `ho-fresh` 的 3 条新用例验证 |
| 宿主语义检查 `offerKnownReadings`：手敲的 `sinx/x` 补上 `\sin\left(\frac{x}{x}\right)`；口述的"根号下 A 加 B"补上 `\sqrt{A}+B` | 开发集 sl-01、zh-04，留出集 ha-05 |
| `max_tokens` 默认值从 500 提到 1200；输出不可用时重问的提示里加一句"内容太长就精简" | 复杂长公式，8 个麦克斯韦方程要用约 400 个 token |
| 评测器：`SUITE=heldout` 切换语料；按 `retry` 字段识别重试用例，原来按类别名识别，漏掉了 `ho-retry` | — |

### 第三轮的发现

18. **在开发集上调出来的规则，确实推广到了留出集。** 3a 版只改了提示词，留出集的 `lim x->0 tanx/x`、`e^(sinx/x)` 就都开始暴露歧义，暴露率从 10–11/14 升到 12–13/14。但开发集里的 `limit->0(sinx/x)` 本身仍然不暴露。
19. **模型对"根号下"类歧义的判断前后不一致。** `根号下x加1` 大多能标出来，`根号下2x减1` 在所有轮次里一次都没标，`四次根号下x加y` 时有时无。提示词写得再明确，也改不掉这种不稳定。
20. **一句"siunitx 单位不支持"会被泛化成误拒。** 模型把所有带单位的量、所有化学式都往越界上套。改成"点名要 siunitx 才算越界"之后，5 条化学式和单位的基线用例、6 条新写的化学式和单位用例全部正常输出。两条仍应越界的新用例（点名 siunitx、用 chemfig 画结构式）也答对了。
21. **两类歧义改由宿主确定性处理。** 手敲斜杠和"根号下"这两类，靠提示词压不住模型的不稳定，按设计稿 D6 预留的 semantic-warning 做成了确定性检查（`packages/core/src/ai/semantic.ts`，有单测）。
    - 只在输入里确实出现了这种结构时才触发。`sin(x)/x`、`sin x/(x+1)`、口述的 over、不带"下"的"根号 x 加 1"都不会触发。
    - 代价是开发集 sc-01 `根号下x的平方加y的平方` 也会多出一个"改为只对 x² 开方"的 chip，于是误报歧义为 1/58。按"宁可多一个 chip，也不藏起一种读法"的原则，这是有意的取舍。
22. **自然发生的 KaTeX 拒绝仍然一次都没出现。** 长尾记号（`sgn`、`arccot`、`lcm`、秩、方差、示性函数、弧……）、化学式、复杂长公式里，模型都直接写出了 KaTeX 支持的写法，比如 `\operatorname{sgn}`、`\mathrm{H_2SO_4}`、`\overgroup`。"带报错重问"这条路径的验证只有三处：构造的重试用例（8/8，三轮相同）、单测，以及第二轮见过的一次真实 JSON 损坏。
23. **长公式逼近 token 上限。** 8 个麦克斯韦方程用了 404 个 token，四阶行列式展开用了 397 个。原来 500 的上限只要再带上 notations 就会被截断，而被截断后重问，回答通常还是一样长，所以把默认值提到了 1200。
24. **延迟略有上升。** 提示词从约 1.1k token 增加到 2.1k token（9 条 few-shot，规则也更长），其中 91% 命中前缀缓存。完整结果 p50 从 749 ms 升到 818 ms，p95 从 1155 ms 升到 1171 ms，所以 p50 比设计稿的 0.8 s 目标高了约 20 ms。首 token 的单次样本在 180–730 ms 之间波动，这 70 ms 里，提示词变长和服务端波动各占多少，现在分不清。
25. **留出集里有一条期望写漏了。** ha-12 `the square root of two x plus one` 有第三种读法 √2·x+1。基线里模型给出了这种读法，而最初的期望里没有，已补上。补的时间是在跑修改后的第一轮之前，依据的是基线结果，不是修改后的结果。

### 浏览器验证

用 `playground-ai` 配置走真实链路：
- `limit->0(sinx/x)` 插入 `\lim_{x \to 0} \frac{\sin x}{x}`，chip 为"改为 sin(x/x)"，正是设计稿 D6 里的那个例子。
- `根号下2x减1` 插入 `\sqrt{2x-1}`，chip 为"改为只对 2x 开方"。

mock 路径的 21 个 Playwright 回归全部通过。

## 第二轮：契约、提示词、解析与重试

第二轮按第一轮的发现，做了这些修复：
- 契约拆出 `notations`。
- 提示词加入作用范围约定、宏包改写、多行环境、等式不给数值等规则，并换掉和语料重叠的 few-shot。
- 实现同步门的 `resolveWithRetry`。
- 修补 JSON，还原被 JSON 转义吞掉的命令。
- 语料扩到 80 条生成加 17 条改写。

提示词迭代了四版（`results/iterations/2*`），歧义暴露率从 4/10 升到 9/10。这一轮的主要发现：

10. 第一轮 5/6 的歧义暴露率有水分：`limit->0(sinx/x)` 原样就是一条 few-shot，换掉之后暴露率掉到 4/10。
11. 作用范围约定会让模型"太有把握"，只加一句"仍标 ambiguous"作用很小，真正起作用的是 few-shot。
12. JSON 模式也会返回坏 JSON，见过两种：少一个右括号；`\,` 没转义。括号配平的坏 JSON 能被 KaTeX 渲染出来，也就是会被当成公式插入。漏转义的 `\frac` 会被悄悄解析成"换页符 + rac"。temperature 0 下，原样重问会拿回同一份坏输出。这些都已修复。
13. 点名要 physics 宏包命令的请求，第一次就被改写成了原生写法。
14. 约 40% 的回答带有 notations，这些不再冒出 chip。
15. 模型仍会给等式声明数值（cv-02）。一致性检查按跳过规则处理，没有误报。
16. 完整结果 p50 749 ms，p95 1155 ms。
17. 三轮之间，80 条里有 77 条输出完全一致。

## 遗留问题与后续

- **指数的作用范围还没定约定。** `e to the x plus one` 三轮里有两轮以 e^{x+1} 为主解释，另一种读法在 chip 里。按 over 和函数名"只作用于紧邻一项"的约定，应该取 e^x+1；但口语里 "x to the n plus one" 常指 x^{n+1}。这是产品决定，定下来之后要写进规则 4，并补一批新用例验证。
- **siunitx 和 physics、mhchem 的处理不对称。** 按原语料 bd-03 的约定，点名要 siunitx 判越界；而点名 physics、mhchem 时是改写成原生写法。统一成都改写，规则会更简单，但这是改变原来的边界约定，需要你拍板。
- **"带报错重问"还没在自然出现的 KaTeX 拒绝上跑过。** 可以留意真实使用中的日志。
- **延迟 p50 818 ms，略超 0.8 s 目标。** 如果要压，可以试减少 few-shot，但要在两套语料上回归。
- `根号x加1` 的主解释偶尔会翻（三轮一次）。
- 区分 syntax 和 unsupported-construct 要等 S3 的能力注册表；chip 的点击切换和 notations 的界面属于 v0.3。
