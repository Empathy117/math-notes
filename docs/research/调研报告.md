# 拆成五层，逐层为 AI 公式编辑器选型

调研的核心结论是：没有哪个现成项目同时做到“AI 只产出公式、渲染后可结构化点击编辑、可切回源码、越界时明确告知、可嵌入其他系统”，但每一项都有成熟的局部实现，而且它们可以拆成互不绑死的五层——持久化什么（真源）、用什么渲染（可分层懒加载）、编辑时挂载什么（结构化编辑器只挂在正在编辑的那个公式上）、AI 输出什么（受 JSON Schema 约束、由宿主校验）、越界由谁判定（宿主的能力注册表，而不是模型自述）。几乎所有笔记与学习产品，包括 Notion、Obsidian、Anki、Jupyter、RemNote、Typora、Overleaf 以及 MathLive 自身，都以 LaTeX 字符串为持久值，结构树只活在内存里。MathLive 是唯一活跃维护、MIT 许可、提供完整结构化编辑的开源 Web 方案，它的命中测试会把点击直接落到被点的子式上；但它会改写被编辑子式的 LaTeX 字面，而且在富文本宿主里的焦点、选区和中文输入法上仍有未解决的问题。Typst 的数学语法更接近口语，交换图可以用 fletcher 在同一个编译器里画出，代价是解包约 28 MB 的编译器包（字体占大头）和 pre-1.0 的破坏性变更，而且六份笔记都没有找到支持 Typst 数学结构化编辑的编辑器。org-mode 新预览系统的“快”来自批处理、预编译格式文件、异步流式解析和哈希缓存，并没有常驻 TeX 进程；到 2026-09 它仍只在 tecosaur 的 fork 上，没有进入 Org 主线。能力边界检测在技术上已经可行：调研团队的本地实验里，KaTeX、MathJax、MathLive、Compute Engine 对 tikz-cd 给出一致且可机读的“未知环境”信号，每次校验不到 1 毫秒。真正的风险不在渲染速度，而在编辑器集成、序列化漂移，以及中文口语数学没有任何公开评测。

> 阅读说明：文中“本地实验”指调研团队 2026-09-25 在 Apple M4 Pro、Node v24.20.0 上用 npm 当日最新版做的测试，引用链接指向对应的 npm 包页面以标明版本；“笔记推断”指研究笔记根据证据推导、未经实测的设计判断。笔记之间的矛盾与未核实事实在正文中就地标出，并在倒数第三节汇总成表。

## 渲染引擎：org 靠摊销提速，JS 渲染器的真正差别在错误信号

### org-latex-preview 的快来自批处理与缓存，而不是常驻进程

先要纠正两个前提。第一，TEC（tecosaur）与 Karthik Chikmagalur 编写的新版 org-latex-preview **到 2026-09 仍未合入 Org 主线**。源码只存在于 tecosaur fork 的 `dev` 分支，`lisp/org-latex-preview.el` 共 3354 行 ([org-latex-preview.el @ dev](https://code.tecosaur.net/tec/org-mode/raw/branch/dev/lisp/org-latex-preview.el))；主线仓库里请求这个文件返回 "Not found"，尚未发布的 10.0 版 ORG-NEWS 也没有相关条目 ([ORG-NEWS](https://cgit.git.savannah.gnu.org/cgit/emacs/org-mode.git/plain/etc/ORG-NEWS))；Org 9.8 发布说明里与预览有关的只有旧系统新增的 `xelatex` 进程和 `org-link-preview` 框架 ([Org Changes](https://orgmode.org/Changes.html))。它原计划随哪个版本发布，笔记之间**说法不一**：源码里的 defcustom 标注 `:package-version '(Org . "9.7")`，另一份笔记根据 2025-08 的邮件列表认为原计划是 9.8 ([emacs-orgmode](https://www.mail-archive.com/emacs-orgmode@gnu.org/msg166227.html))。两边一致的是，2025 年中它仍处在 pre-patch 阶段，合入没有公开时间表。第二，源码里**找不到常驻 TeX 进程**，grep "persistent|daemon|server" 只命中 org-persist 缓存的说明；常驻进程这种模式只在 Zulip 的 KaTeX 服务里真实存在（见本节末尾）。

它的速度是**摊销**出来的，由四个机制叠加。一个 buffer 里所有待渲染片段写进同一个 .tex，每个片段包一层 `preview` 环境、成为 DVI 的一页，preamble 追加 `\usepackage[active,tightpage,auctex,dvips]{preview}`。preamble 用 mylatexformat dump 成 .fmt，以 sha1 为键缓存在 `org-persist`，之后整段 preamble 被替换成一行 `%&`；这一步**只对 pdflatex 有效**，xelatex 和 lualatex 下会提示不支持 ([ox-latex.el @ dev](https://code.tecosaur.net/tec/org-mode/raw/branch/dev/lisp/ox-latex.el))。编译通过 `org-async-call` 异步启动，filter 边读 stdout 边切分，dvipng 路径用 `--follow` 与 LaTeX 并发出图。生成的 SVG/PNG 按处理方式、preamble、片段文本、颜色与编号的 sha1 缓存。逐片段报错靠一个巧妙的手法：preview.sty 的 `auctex` 选项会在每个片段首尾打印伪造的错误行 `! Preview: Snippet N started.` 与 `! Preview: Snippet N ended.(H+D x W)`，正则切分后既拿到该片段的错误文本，又拿到用于基线对齐的 depth、height、width；输出若中途中断，就把第一个缺图片段的前一个标为坏片段，再重跑其余片段 ([org-latex-preview.el @ dev](https://code.tecosaur.net/tec/org-mode/raw/branch/dev/lisp/org-latex-preview.el))。实时预览用 `org-latex-preview-mode-update-delay` 防抖（默认 1 秒，Karthik 的示例配置是 0.25），再按最近 3 次耗时的均值自适应节流 ([abode.karthinks.com](https://abode.karthinks.com/org-latex-preview/))。

公告中“每秒处理数百个片段”的说法 ([emacs-orgmode 2023-05](https://lists.gnu.org/archive/html/emacs-orgmode/2023-05/msg00207.html)) **没有找到可复现的基准**。作为对照，Org 现行的旧系统为每个片段单独建临时 tex，经 `shell-command` 同步编译 ([org.el](https://cgit.git.savannah.gnu.org/cgit/emacs/org-mode.git/plain/lisp/org.el))，Karthik 2022 年写道它在中等规模文档上首次调用会让 Emacs 卡住约一分钟 ([karthinks.com](https://karthinks.com/software/fast-latex-previews-in-org-mode/))。这套设计优化的是吞吐，不是单个公式的延迟：交互编辑一个公式时，“起进程、读 fmt、跑 dvisvgm”的下限仍然存在，所以它才需要秒级防抖。对 Web 组件而言，它适合作为服务器端“真 TeX 层”的蓝本，替代不了前端的即时渲染。顺带一提，光标进入片段时自动关预览、离开时重开的 org-fragtog 只是调用 Org 已有的预览功能，最后一个 release 停在 2022 年 ([org-fragtog](https://github.com/io12/org-fragtog))。

### 三个 JS 渲染器：错误信号的质量比速度更重要

KaTeX 是同步渲染器，管线为 Lexer 与宏展开、Parser、buildHTML/buildMathML；字体度量表由 `buildMetrics.sh` 在构建期生成，排版不测量 DOM、不引发回流 ([fontMetricsData.js](https://raw.githubusercontent.com/KaTeX/KaTeX/main/src/fontMetricsData.js)；[katex.org](https://katex.org/))。它的 `ParseError` 带 `position`（0 基）、`length` 与 `rawMessage`，可以直接变成编辑器里的错误下划线 ([ParseError.ts](https://raw.githubusercontent.com/KaTeX/KaTeX/main/src/ParseError.ts))；不过 `throwOnError:false` **只兜得住 ParseError**，其他异常仍会抛出 ([katex.mjs 0.18.9](https://cdn.jsdelivr.net/npm/katex@0.18.9/dist/katex.mjs))。`strict` 可传函数收集 `unknownSymbol`、`unicodeTextInMathMode` 等告警，`macros` 配合 `globalGroup` 能在多个公式间共享笔记级宏，`maxExpand` 默认 1000 防止宏无限展开 ([KaTeX Options](https://katex.org/docs/options))。0.18.9 的 `katex.min.js` 约 **76 KB gzip**，字体按用到的字形懒加载 ([jsDelivr](https://cdn.jsdelivr.net/npm/katex@0.18.9/dist/katex.min.js))；项目非常活跃，但 0.17 和 0.18 各带一次破坏性变更，分别涉及内部 `__defineFunction` 和 CSS 类名前缀 ([CHANGELOG](https://raw.githubusercontent.com/KaTeX/KaTeX/main/CHANGELOG.md))。

MathJax 4 的结构是 input jax → 内部 MathML 树 → output jax，覆盖面在 JS 渲染器里最广：physics、mhchem、amscd、bussproofs、mathtools、empheq 都有扩展，其中 amscd、bussproofs、mhchem 等在首次遇到对应宏时自动加载，physics、mathtools 则要显式加载 ([MathJax autoload](https://docs.mathjax.org/en/latest/input/tex/extensions/autoload.html))。它的弱点在错误信号上。`TexError` 只有 `id` 与消息，**不带源码位置** ([TexError.ts](https://raw.githubusercontent.com/mathjax/MathJax-src/master/ts/input/tex/TexError.ts))；除 `input/tex-base` 外，所有 TeX 组件都预装了 `noundefined`，未知宏被画成红字而公式照常输出 ([noundefined](https://docs.mathjax.org/en/latest/input/tex/extensions/noundefined.html))，要拿它做回退检测，就得先去掉这个包或检查输出里的红字。4.1.3 的 `tex-chtml.js` 约 **281 KB gzip**，`tex-svg.js` 约 615 KB ([tex-chtml.js](https://cdn.jsdelivr.net/npm/mathjax@4.1.3/tex-chtml.js))，默认的 `inlineMath` 不包含 `$...$` ([TeX Input Options](https://docs.mathjax.org/en/latest/options/input/tex.html))。唯一能查到的速度对比，是维护者 Davide Cervone 2020 年给出的“v3 约比 KaTeX 慢 2.7 倍” ([mathjax-users](https://groups.google.com/g/mathjax-users/c/aboJLMb50uQ/m/Y77FexF_AwAJ))，这是**旧数据**，2024 到 2026 年没有独立基准。

Temml 只输出 MathML、把排版交给浏览器，`temml.min.js` 约 **50 KB gzip**，是三者中最轻的。它内置 `\label`/`\ref`/`\eqref` 和 `multline`，physics 与 mhchem 以扩展提供，`annotate` 选项可以把 TeX 源写进 `<annotation>`；和 KaTeX 相反，它**默认 `throwOnError:false`**，要拿到 `position` 必须显式打开 ([Temml Administration](https://temml.org/docs/en/administration.html)；[temml.mjs](https://cdn.jsdelivr.net/npm/temml@0.13.5/dist/temml.mjs))。浏览器 MathML 的全球支持率约 95.17%（Chrome/Edge 109+）([caniuse](https://caniuse.com/mathml))，但渲染质量取决于各浏览器的 MathML Core 实现。至于 Temml 的来历，“KaTeX fork”的说法只见于二手资料，笔记本身只核实到两者的 `ParseError` 与 `renderError` 代码结构几乎一致。

表中有一处笔记之间的**矛盾**：Temml 官方对比页把 `{CD}` 标为只有 Temml 与 MathJax 部分支持 ([Temml comparison](https://temml.org/docs/en/comparison.html))，而 KaTeX 文档列出了 `CD`，本地实验里 KaTeX 0.18.9 也直接渲染通过；笔记推测对比页只评估了 MathML 输出。可以确定的是，tikz-cd、xymatrix、TikZ/pgfplots、chemfig 超出了所有 JS 渲染器的能力，这堵墙几乎都落在“图”而不是“公式”上。

浏览器内的“真 TeX”有三类。busytex 及其 TeXlyre 派生版把 TeX Live 2026 的多个二进制编进一个 WASM，**WASM 约 32 MB、数据包 90–400 MB**，靠 Emscripten 的 IndexedDB 缓存跨刷新保留 ([texlyre-busytex](https://github.com/TeXlyre/texlyre-busytex))，而且二进制列表里没有 dvisvgm，只能出 PDF ([busytex](https://github.com/busytex/busytex))；SwiftLaTeX 最后一个 release 停在 2022 年 ([SwiftLaTeX](https://github.com/SwiftLaTeX/SwiftLaTeX))；tectonic 没有官方浏览器版，只有 Go/wazero 的 WASI 封装 tecgonic，它的 1360 ms/op 测的是 WASM 实例化而不是 LaTeX 编译 ([tecgonic](https://pkg.go.dev/github.com/mgilbir/tecgonic))。对图表最实用的是 drgrice1/tikzjax：把 TeX 的 Pascal 源码编成 WASM、预载格式，包含 tikz-cd 与 pgfplots，经 dvi2html 直接输出 SVG，每个脚本首次运行后缓存结果 ([drgrice1/tikzjax](https://github.com/drgrice1/tikzjax))；Obsidian 的 TikZJax 插件在此基础上内置了 chemfig、circuitikz ([obsidian-tikzjax](https://github.com/artisticat1/obsidian-tikzjax))。数学专用的非 TeX 移植有 2026 年新出的 Rust 项目 RaTeX（对标 KaTeX，WASM 加原生后端）和低活跃的 C++ 库 MicroTeX，前者的体积与成熟度未核实 ([RaTeX](https://ratex.lites.dev/)；[MicroTeX](https://github.com/NanoMichael/MicroTeX))。这些引擎在浏览器里的首次与后续编译延迟，**笔记没有找到任何可靠数据**。

真实产品的分层有几种形态。Overleaf 编辑器里用 MathJax 预览，`package.json` 依赖 `"mathjax": "^4.1.2"`，`load-mathjax.ts` 禁用了 `require` 与 `textmacros`，PDF 则由服务器 TeX 编译 ([overleaf package.json](https://raw.githubusercontent.com/overleaf/overleaf/main/services/web/package.json)；[load-mathjax.ts](https://raw.githubusercontent.com/overleaf/overleaf/main/services/web/frontend/js/features/mathjax/load-mathjax.ts))。MediaWiki 先用 texvc 白名单校验输入，再在服务端生成 MathML 或交给客户端 MathJax ([Extension:Math](https://www.mediawiki.org/wiki/Extension:Math))。Anki 与 Obsidian 让用户手动选层，Anki 官方还警告本地 LaTeX 方式可能读写本机文件 ([Anki Manual](https://docs.ankiweb.net/math.html))。intmath 据称先用 KaTeX、失败再交给 MathJax，但原页返回 403，**未能核实** ([intmath](https://www.intmath.com/blog/mathematics/katex-with-asciimathml-input-and-mathjax-fallback-9456))。服务端 JS 渲染的关键是常驻进程：Zulip 关掉独立 KaTeX 服务后，一条消息里有几十个公式时甚至可能发送失败 ([Zulip](https://zulip.readthedocs.io/en/latest/production/system-configuration.html))；GitLab 则用配额防滥用，只渲染前 1000 个行内公式 ([GitLab](https://docs.gitlab.com/user/markdown/))。笔记没有找到任何开源笔记产品实现“JS 渲染器失败后自动升级到服务器 TeX”，现有先例都是用户手动选层。

## Typst 让输入更像口语、让交换图同源，代价是 28 MB 与版本漂移

### 语法离用户的口语输入只差几个字符

Typst 数学本身就是一种没有反斜杠和花括号的线性记法：`$...$` 进入数学模式，`_`、`^`、`/` 构成结构，`mat(1, 2; 3, 4)`、`cases(...)`、`op(...)` 直接可写，也不需要 amsmath 之类的包 ([Typst Math](https://typst.app/docs/reference/math/)；[Guide for LaTeX Users](https://typst.app/docs/guides/for-latex-users/))。把用户的例子映射过去几乎是最小编辑距离：定积分写作 `integral_1^2 (x+1)^2 dif x`，“limit->0(sinx/x)”写作 `lim_(x -> 0) (sin x)/x`，只需把 `dx` 改成 `dif x`、把 `limit` 换成预定义算符 `lim` ([op](https://typst.app/docs/reference/math/op/))。代价是“连写多个字母即变量名”：`sinx`、`dx` 都会报 `unknown variable`，但编译器会附上“字母间加空格”或“加引号当文本”两条 hint ([typst#5029](https://github.com/typst/typst/issues/5029))，这对 AI 层是可预测、可机读的自动修复触发器。`"if x is even"` 这样的字符串和 `#` 代码逃逸，让自然语言片段可以直接嵌进公式。需要强调的是，笔记**没有找到任何“非正式输入 → Typst”或“LLM 生成 Typst 数学”的准确率测评**，这些优势目前停留在语法层面的推断。

### 速度与体积：文档级有数据，公式级是空白

Typst 编译器是无状态的四阶段管线（parse → eval → layout → export），解析永不失败，语法错误变成 error node；增量解析只在局部重分配 span、让远处的 span 编号保持稳定，以提高缓存命中 ([architecture.md](https://github.com/typst/typst/blob/main/docs/dev/architecture.md))。comemo 的“受约束记忆化”只记录函数实际访问过的数据，在模块、闭包、元素三个粒度复用结果 ([comemo](https://github.com/typst/comemo))。公开实测只有文档级数据：Zed 的实时预览 RFC 在 tinymist 管线上测得一份 5 页文档**记忆化编译 26 ms、冷编译 624 ms**（原生）([Zed #51633](https://github.com/zed-industries/zed/discussions/51633))；TUGboat 2026 论文附带的可复现基准发现，**0.14 及以后版本每次增量编辑比 0.12/0.13 慢 1.6–2.2 倍**（300 页文档）([luatex-benchmark](https://github.com/texlode/luatex-benchmark))，“越新越快”并不成立。**没有任何来源给出单个公式在原生或 WASM 下的编译加渲染耗时**；一篇 Medium 文章声称 5–10 页文档 30–50 ms、WASM 压缩后 2.8 MB，但页面返回 403，数字只来自搜索摘要，无法核实。

浏览器端的事实标准是 Apache-2.0 的 typst.ts：`@myriaddreamin/typst-ts-web-compiler` 0.7.0 **解包后 28.4 MB**，`typst-ts-renderer` 0.7.0 约 1.09 MB ([npm web-compiler](https://www.npmjs.com/package/@myriaddreamin/typst-ts-web-compiler)；[npm renderer](https://www.npmjs.com/package/@myriaddreamin/typst-ts-renderer))；稳定版仍停在 Typst 0.14.2，要用 0.15 得上 0.8.0-rc 系列 ([typst.ts releases](https://github.com/Myriad-Dreamin/typst.ts/releases))。这里有一处**日期矛盾**：同一 releases 页的 HTML 抓取摘要把这些版本标成 2025 年，Atom 源给出带时间戳的 2026 年；笔记采信 2026，旁证是 tinymist 在 2026-09-04 才升级到 0.8.0-rc3 ([tinymist releases](https://github.com/Myriad-Dreamin/tinymist/releases))。体积大头是字体：另一个项目的 spike 测得引入 Typst 渲染后 WASM 增加 **42.8 MB 原始 / 16.4 MB gzip**，归因于 `typst-assets` 内嵌的字体，但作者自己提醒这些数字要重跑一遍才能信 ([Rustume#682](https://github.com/lgtm-hq/Rustume/issues/682))。默认包还会从 GitHub 下载字体，需要 `disableDefaultFontAssets` 和按需字体加载来控制 ([typst.ts](https://github.com/Myriad-Dreamin/typst.ts)；[snippet.mts](https://github.com/Myriad-Dreamin/typst.ts/blob/main/packages/typst.ts/src/contrib/snippet.mts))。2026-07 出现的 `typst-wasm` 主打多运行时一致的 API，许可、体积、跟踪的 Typst 版本都没查到 ([Typst Forum #9399](https://forum.typst.app/t/typst-wasm-compile-typst-in-browsers-node-and-serverless-runtimes/9399))。浏览器端首次加载、WASM 实例化与单次渲染的毫秒数，**没有任何一手数据**。另外，comemo 的缓存只在同一个编译器实例内有效，所以浏览器端需要在 Web Worker 里长驻一个实例，每次新建或 `reset()` 都会丢掉增量优势（笔记推断）。

### 错误、互转与图表：优势和代价都是结构性的

typst.ts 自 PR #492 起让 `compile()` 在结果里返回结构化诊断，`diagnostics:'full'` 时每条是 `{package, path, severity, range, message}`，`range` 为“行:字符”区间 ([compiler.mts](https://github.com/Myriad-Dreamin/typst.ts/blob/main/packages/typst.ts/src/compiler.mts)；[PR #492](https://github.com/Myriad-Dreamin/typst.ts/pull/492))。但常用的高层 `TypstSnippet`（即 `$typst.svg()` 等）默认 `diagnostics:'none'` ([snippet.mts](https://github.com/Myriad-Dreamin/typst.ts/blob/main/packages/typst.ts/src/contrib/snippet.mts))；诊断**没有错误码**，JS 类型里也看不到 hints（是否携带未核实）。要识别“未知变量”“包缺失”只能正则匹配 message，而 message 措辞在版本间改过 ([typst#6433](https://github.com/typst/typst/pull/6433))，匹配规则必须与 Typst 版本绑定并配回归测试。与 KaTeX 的 `position`/`length` 相比，Typst 是“整段要么成功、要么给出诊断列表”，出错时显示上一次成功的 SVG 这类降级要宿主自己做。

与 LaTeX 的互换存在明确上限。Typst 社区明确拒绝在编译器里原生支持 LaTeX 数学，理由是要正确处理 LaTeX 数学就得实现一个完整的 LaTeX 引擎，宏展开与 Typst 的纯函数模型冲突 ([Typst Forum #6755](https://forum.typst.app/t/can-typst-natively-support-latex-math/6755))。三条工具链各司其职：MiTeX 是约 185 KB 的 Typst 内 WASM 插件，把 LaTeX 就地转成 Typst 内容，32.5k 个公式 WASM 耗时 2.28 s，但它产出的是渲染结果，不是给人继续编辑的 Typst 源 ([mitex](https://github.com/mitex-rs/mitex))，论坛给出的“至少九成”只是**主观估计**；tex2typst 是纯 JS 的双向转换器（`tex2typst()`/`typst2tex()`，0.3.15 起改为 Apache-2.0）([tex2typst](https://github.com/qwinsi/tex2typst))；pandoc 3.1.2 起有 Typst writer，texmath 能写 Typst 数学但不能读 ([pandoc 3.1.2](https://hackage.haskell.org/package/pandoc-3.1.2/changelog)；[texmath](https://hackage.haskell.org/package/texmath))。三者都在追 Typst 的符号改名（例如 0.14 的 `\langle` ↔ `chevron.l`），所以“Typst 版本 ↔ 转换器版本”必须成对锁定，而**没有任何量化的互转保真度基准**。两份笔记对 tex2typst 的发布日期也有**矛盾**：Typst 笔记列出 v0.5.0（2025-11-29）到 v0.6.2（2026-06-14），存储格式笔记的抓取摘要却给出 2023-12 至 2024-06，后者与“跟进 Typst 0.14 符号变更”的说明自相矛盾，需要复核 ([tex2typst releases](https://github.com/qwinsi/tex2typst/releases))。

图表是 Typst 路线最大的结构性优势。fletcher（MIT，需要 Typst ≥ 0.13 与 CeTZ ≥ 0.3.4）能画交换图、流程图、Feynman 图，cetz（LGPL-3.0）是受 TikZ 启发的纯 Typst 绘图库，两者都不带 WASM 插件 ([fletcher](https://github.com/Jollywatt/typst-fletcher)；[cetz](https://github.com/cetz-package/cetz))，理论上和公式走同一个编译器、同一种语法，同样输出 SVG；而 LaTeX 路线要画 tikz-cd 只能靠 TikZJax 或服务器 TeX。typst.ts 维护者确认，只要客户端能访问 packages.typst.org 就能加载包，连带 WASM 插件的包也可以 ([discussion #731](https://github.com/Myriad-Dreamin/typst.ts/discussions/731))，Obsidian 的 Typst Mate 也声称几乎所有 Typst 包都能用 ([Typst Mate](https://github.com/azyarashi/obsidian-typst-mate))；但**没有 cetz/fletcher 在浏览器 WASM 里运行的直接案例或延迟数据**，Quarto 社区有人渲染 fletcher 图屡屡失败，根因没有查明 ([quarto #12439](https://github.com/orgs/quarto-dev/discussions/12439))。cetz 的 LGPL-3.0 在商用分发前需要法务确认。

输出与先例方面，Typst 0.15（2026-06-15）让 HTML 导出原生输出 MathML ([Typst 0.15 blog](https://typst.app/blog/2026/typst-0.15/))，但整个 HTML 导出仍是实验特性，官方明确要求不要用于生产 ([Typst HTML](https://typst.app/docs/reference/html/))，追求视觉一致时仍建议 SVG。已有的 Typst 数学笔记项目给出两条教训：停更风险是真实的，fenjalien/obsidian-typst 停在 Typst 0.11（2024-03）([obsidian-typst](https://github.com/fenjalien/obsidian-typst/blob/master/README.md))；兼容 LaTeX 用户需要回退层，obsidian-wypst 遇到 `\begin{...}` 或 `\<symbol>` 就切回 MathJax ([obsidian-wypst](https://github.com/0xbolt/obsidian-wypst))，Emacs 的 org-typst-math 则用长驻 Rust helper 保留字体库与编译缓存，导出时把所有公式合成一个批量 JSON-RPC 请求 ([org-typst-math](https://github.com/DzmingLi/org-typst-math))。对本需求最关键的是：**六份笔记都没有找到支持 Typst 数学结构化点击编辑的编辑器**。MathLive 自 0.106.0 起能 `getValue('typst')` ([MathLive CHANGELOG](https://github.com/arnog/mathlive/blob/master/CHANGELOG.md))，但那只是单向导出。选 Typst 做真源，要么自建结构化编辑器，要么经 LaTeX 转换往返，后者会引入上文所说的有损转换。

## MathLive 是唯一现成的结构化答案，但它会改写你的 LaTeX

### 五类内部模型决定了能否精确导出 LaTeX

结构化编辑器的内部模型大致分五类，直接决定了它们能否精确导出 LaTeX。MathLive 用 `Atom` 树：子节点放在命名 branch（`body`、`above`、`below`、`superscript`、`subscript`）里，矩阵用 `[row, col]` 作 cell branch，每个 atom 记录解析时对应的原始 token 片段 `verbatimLatex` ([atom-class.ts](https://github.com/arnog/mathlive/blob/master/src/core/atom-class.ts)；[parser.ts](https://github.com/arnog/mathlive/blob/master/src/core/parser.ts))；它还自带按 TeXbook 规则定位上下标的排版引擎，不依赖 KaTeX 或 MathJax。MathQuill 是 DOM 与节点一一绑定的双向链表树，LaTeX 完全由树重新生成、不保留原始拼写，遇到未知命令时整体解析失败并清空内容 ([latex.ts](https://github.com/mathquill/mathquill/blob/master/src/services/latex.ts))。Wiris MathType 与 Word 以 MathML/OMML 为内部或交换格式，LaTeX 只是导入导出；TeXmacs 与 LyX 用自有的树；Tiptap Mathematics、prosemirror-math、ckeditor5-math、TinyMCE Math 则根本不是结构化编辑器，只是“LaTeX 文本框加渲染”。要精确导出 LaTeX 只有两条路：以 LaTeX 字符串为唯一真源，或者做源码区间跟踪——MathLive 的 `verbatimLatex` 和 TeXmacs 的 source tracking 都属于后者。

### 点哪改哪在 MathLive 里是默认行为

用户要的“点极限下标里的 0 直接改”，在 MathLive 里由默认的指针处理完成（据源码推断，未实测）。命中测试先用 `getAtomBounds()` 递归找到离点击点平方距离最近的最深 atom，再沿 parent 链找第一个设置了 `captureSelection` 的祖先，最后按 `bias` 与竖直中线决定落在左侧还是右侧，得到一个整数 offset；矩阵先按竖直距离定行，只在该行的 cell 里搜索 ([pointer-input.ts](https://github.com/arnog/mathlive/blob/master/src/editor-mathfield/pointer-input.ts))。整棵树被线性化成整数 offset ([model-private.ts](https://github.com/arnog/mathlive/blob/master/src/editor-model/model-private.ts))，因此公开 API 很像 textarea：`getOffsetFromPoint(x, y, {bias})`、`position`、`selection`（`{ranges, direction}`）、`getValue(start, end, format)`、`insert(s, {insertionMode: 'replaceSelection', selectionMode: 'placeholder'})`、`executeCommand()`；事件有 `move-out`（方向键在字段内无处可去时带 `detail.direction` 触发）、可取消的 `beforeinput` 和 `selection-change` ([MathLive API](https://mathlive.io/mathfield/api/)；[Interacting guide](https://mathlive.io/mathfield/guides/interacting/))。在 `readOnly` 的字段里用 `\placeholder[id]{…}` 可以做到“只有指定位置可改” ([Fill-in-the-blank](https://mathlive.io/mathfield/guides/fill-in-the-blank/))，这与“点某个数改掉它”的交互很接近。缺口有两个：MathLive **没有公开“LaTeX 字符偏移 ↔ model offset”的映射**，要在源码视图里高亮当前选中的子式，只能自研带 span 的解析器；MathQuill 的公开 API 只能全选或清除选区，无法按区间设置或读取选区的 LaTeX ([Api_Methods.md](https://github.com/mathquill/mathquill/blob/master/docs/Api_Methods.md))。

### 往返漂移是必须提前设计的问题

往返是 MathLive 最需要提前设计的地方。序列化时，未被改动的 atom 原样返回 `verbatimLatex`；子式一旦被编辑，`isDirty` 会让该 atom 及失效的祖先改用规范形式重写，而默认形式是“紧凑”的：输出 `\frac12` 而不是 `\frac{1}{2}`，`\sqrt2`、`x^2` 同理 ([atom-class.ts](https://github.com/arnog/mathlive/blob/master/src/core/atom-class.ts))。2026-08-03 开启的 #3055 提议新增 `MathfieldElement.compactSerialization` 开关，理由正是服务端解析器与判分系统需要稳定拼写，读取时仍未合并、未见维护者回应 ([#3055](https://github.com/arnog/mathlive/issues/3055))；#3078（2026-09-21）报告 `defaultMode` 为 text 时文本段导出不带 `\text{}`。序列化规则还会随版本变化：0.104.0 起非标准三角函数改用 `\operatorname{}`，0.108.0 修正了字体样式的序列化 ([CHANGELOG](https://github.com/arnog/mathlive/blob/master/CHANGELOG.md))。TeXmacs 的经验说明“以树为真源又要保真”代价很高：它的 conservative conversion 要在源文档里插入 marker、用 `invariant` 标签包住未改动的原始源码、带与不带 marker 各转换一次并把结果不一致的 marker 拉黑，作者承认仍在为用户宏和元数据挣扎，而当时各种 LaTeX→MathML 转换器的成功率只有 2% 到 54% ([latexconv](https://www.texmacs.org/joris/latexconv/latexconv.html))。LyX 把不认识的命令保留为 `InsetMathUnknown`，结构之外的内容用 ERT（TeX Code）原样透传 ([LyX Math manual](https://elyxer.nongnu.org/lyx/Math.html))。这些先例指向同一条规则：未知内容必须作为“不透明但原样序列化”的节点保留，保存时自检 `serialize(parse(s)) === s`，不相等就保留原字符串（笔记推断）。

### 覆盖面、安全与维护状态都有需要锁定的细节

覆盖面上，MathLive 支持 800 多个命令，0.104.0 起支持 `align`、`gather`、`multline`、`split` 等多行环境，`\ce{}` 和 braket 也在列 ([Commands reference](https://mathlive.io/mathfield/reference/commands/))。未知命令会变成 `ErrorAtom` 并记为 `unknown-command`，而不是让整个公式失效 ([parser.ts](https://github.com/arnog/mathlive/blob/master/src/core/parser.ts))；`ParserErrorCode` 共 14 种，另有 `mf.errors` 与独立导出的 `validateLatex()` ([core-types.ts](https://github.com/arnog/mathlive/blob/master/src/public/core-types.ts))。它**不支持 amscd `CD`，也没有 `\label`、`\tag`、`\ref`**，所以 KaTeX 能渲染的简化交换图在 MathLive 里不可编辑。安全方面，0.110.0 才修复 #3028：此前 `\text{}` 里的 `<img src=x onerror=…>` 可以执行脚本，渲染任何同步而来或 AI 生成的不可信 LaTeX 都必须用 0.110.0 以上 ([CHANGELOG](https://github.com/arnog/mathlive/blob/master/CHANGELOG.md))。本地实验还发现，`validateLatex` 对缺右括号的 `\frac{1}{x` 和 `\ce{H2O}` 都返回空数组，返回的 `before`/`after` 看起来与字段名相反 ([本地实验，mathlive 0.110.0](https://www.npmjs.com/package/mathlive))，它适合做 lint，不适合单独充当语法裁判。

代价是体积与单点维护。bundlephobia 测得 MathLive 0.110.0 为 **822 KB minified / 225 KB gzip**，字体与音效另从 URL 加载，而 KaTeX 约 77 KB gzip ([bundlephobia](https://bundlephobia.com/package/mathlive@0.110.0))。npm 上只有 arnog 一位 maintainer，按每年约 6 月和 1 月两个大版本的节奏发布 ([npm registry](https://registry.npmjs.org/mathlive)；[README](https://github.com/arnog/mathlive))，于是出现了一批第三方 fork：`@lofcz/mathlive` 从 2026-08 起连发 11 个补丁版，`mathlive-chemistry` 让 `\ce{}` 可编辑并支持简化的 `\chemfig` ([mathlive-chemistry](https://www.npmjs.com/package/mathlive-chemistry))，`mathlive-tera` 的版本号 0.120.10 高于上游、repository 字段却指向上游，存在供应链混淆风险 ([mathlive-tera](https://www.npmjs.com/package/mathlive-tera))；笔记没有找到 npm 所有权转移的证据。MathJSON 解耦的时间点上，两份笔记**直接冲突**：结构化编辑器笔记依据 npm 元数据（0.110.0 仍依赖 `@cortex-js/compute-engine` 0.58.0）和 Interacting 指南，认为已发布的 0.110.0 仍有 `expression` 属性与 `"math-json"` 格式，移除只写在 master 的 `[Unreleased]` 段；存储格式笔记则写成“0.110.0 起移除” ([Interacting guide](https://mathlive.io/mathfield/guides/interacting/)；[CHANGELOG](https://raw.githubusercontent.com/arnog/mathlive/master/CHANGELOG.md))。npm 依赖这条硬证据更支持前者，但无论哪种，下一个大版本都会移除，集成时应以实际安装版本为准。`validateLatex` 的 `macros` 选项也有类似分歧：两份笔记依据 changelog 记为 0.110.0 新增，另一份依据搜索摘要记为 0.106.0。

无障碍与移动端还有未关的问题。#3081（2026-09-23）指出 shadow DOM 里接收键盘输入的 `ML__keyboard-sink` 没有 accessible name，宿主上的 `role="math"` 还会触发 axe 的 nested-interactive 违规 ([#3081](https://github.com/arnog/mathlive/issues/3081))；虚拟键盘由 `mathVirtualKeyboardPolicy` 控制，iPad 物理键盘的组字问题自 2022 年起一直未关 ([Virtual keyboard](https://mathlive.io/mathfield/virtual-keyboard/)；[#1734](https://github.com/arnog/mathlive/issues/1734))。对中文用户最直接的是 #3058：Windows + Chrome + 微软注音输入法下，`insert()` 一个带 placeholder 的分式后按数字键，组字开始时会无条件删除当前选区，结果是 `3` 而不是 `\frac{3}{…}`，而且报告者指出程序化输入绕过了输入法、自动化测试无法复现 ([#3058](https://github.com/arnog/mathlive/issues/3058))。MathQuill 作为替代品已经明显落后：npm 包停在 0.10.1-a（2022-08），上游 2025-06 之后没有推送，README 却仍称项目在恢复活跃开发；Desmos 的 fork 仍在更新，但没有发布到 npm ([mathquill npm](https://registry.npmjs.org/mathquill)；[desmosinc/mathquill](https://github.com/desmosinc/mathquill))。

### 底部输入框可以借鉴线性输入法的 autobuildup

底部输入框本质上是一个“线性输入法”，这方面最成熟的规范是 UnicodeMath。UTN #28 v3.3（2025-01-22）把 auto build-up 定义为**由运算符优先级驱动的增量解析**：每当键入的字符（空格、二元或关系运算符、右括号等）让它前面的文本成为无歧义的线性格式，就把这段文本构建成二维结构，并吃掉触发字符；分子分母、上下标最外层的括号在构建时剥掉，`sin` 等函数名后接不可见的函数应用符 U+2061 ([UTN28 v3.3](https://www.unicode.org/notes/tn28/UTN28-PlainTextMath-v3.3.pdf))。Word 的 Formula Autobuildup 就是这样工作的 ([Murray Sargent](https://learn.microsoft.com/en-us/archive/blogs/murrays/formula-autobuildup-in-word-2007))，Web 上唯一的实现是 MIT 许可的 UnicodeMathML，它接受 UnicodeMath、LaTeX 与英文口述等输入，并支持从 MathML 反向 build down ([UnicodeMathML](https://murrayiii.github.io/UnicodeMathML/))。AsciiMath 与 mathup 是一次性的宽松解析，没有增量语义 ([asciimath.org](http://asciimath.org/)；[mathup](https://github.com/runarberg/mathup))；MathLive 则用 inline shortcuts 和 `#@`/`#?` 模板在结构模型上即时变换，0.99 起支持“转换后立即按 Backspace 撤销转换” ([Shortcuts guide](https://mathlive.io/mathfield/guides/shortcuts/)；[CHANGELOG](https://github.com/arnog/mathlive/blob/master/CHANGELOG.md))。TeXmacs 的语义编辑研究给这类确定性方案划出了上限：它在后台用 packrat parser 从外观推断语义，纠错启发式把三组真实文档的错误从 2,821 降到 705、4,158 降到 543、308 降到 86，剩余错误绝大多数来自不可见乘号与函数应用的歧义 ([semedit](https://www.texmacs.org/joris/semedit/semedit.html))。从外观推断语义，再怎么纠错也会残留歧义，这正是 AI 层要承担、也要主动暴露给用户的部分。

## 点击不塌缩的成本，取决于编辑器把什么当真相源

### 五类交互模型里，用户要的是 B 与 C 的组合

笔记产品里的行内公式交互可以归为五类。A 类是光标进入即就地展开源码，Obsidian Live Preview、Overleaf Visual Editor、Zettlr、Typora 和 org-mode 配 org-fragtog 都属此类 ([Obsidian Help](https://obsidian.md/help/edit-and-read)；[Typora](https://support.typora.io/Markdown-Reference/))；B 类是原子节点加锚定弹层，包括 Notion、RemNote、AFFiNE/BlockSuite、Milkdown Crepe、Plate 和 Tiptap 的 `onClick` 回调 ([Notion](https://www.notion.com/help/math-equations)；[RemNote](https://help.remnote.com/en/articles/6565191-writing-equations-with-latex)；[Plate](https://platejs.org/docs/equation))；C 类是就地结构化编辑，如 Mathcha、Word、Google Docs 与 MathLive 控件；D 类整块切换源码与渲染，如 Logseq、Jupyter、marimo；E 类是 Apple Math Notes 那种“键入等号即求值”的计算型建议 ([Apple Support](https://support.apple.com/guide/notes/solve-math-apda85974595/mac))。用户要的“点击不退化成源码”是 B、C 类的默认行为；A 类默认塌缩，而且代价看得见：Obsidian 收起长公式时视口跳动、光标在屏幕上大幅上移，这个 2023 年报告的问题在 2026-08 被移进“Bug Graveyard”，至今未解决 ([Obsidian Forum #66219](https://forum.obsidian.md/t/when-collapsing-equations-for-live-preview-leave-cursor-at-the-same-position-relative-to-the-screen/66219))；Overleaf 在代码模式下用“光标上方 8px 的实时预览 tooltip”部分补偿 ([math-preview.ts](https://raw.githubusercontent.com/overleaf/overleaf/main/services/web/frontend/js/features/source-editor/extensions/math-preview.ts))。几个细节可以直接借鉴：Notion 与 RemNote 让方向键移到公式上就自动打开编辑器；Obsidian 的“Toggle Live Preview/Source mode”命令是全局源码开关的先例；RemNote 允许在公式里选中局部后点“Create Cloze”做挖空卡片，并把自然语言到 LaTeX 的 AI 建议做成按 Tab 接受 ([RemNote](https://help.remnote.com/en/articles/6565191-writing-equations-with-latex))——这是“选中公式局部、对局部施加动作”最接近的产品先例。

### 源码加装饰，还是结构化文档树

两条架构路线的本质区别在真相源。CodeMirror 6 路线以纯文本为真相，公式只是 `Decoration.replace` 加 `WidgetType` 的视图层替换，改变垂直布局的装饰必须由 StateField 直接提供，`EditorView.atomicRanges` 让光标跳过 widget ([CodeMirror Decoration](https://codemirror.net/examples/decoration/))。Overleaf 的实现是：选区与公式区间相交就不装饰（`shouldDecorate = state.readOnly || !selectionIntersects(state.selection, extents)`），鼠标按住期间冻结装饰重算；`MathWidget.eq()` 在 LaTeX、displayMode、preamble 都不变时复用 DOM，并把实测高度缓存为 `estimatedHeight` ([atomic-decorations.ts](https://raw.githubusercontent.com/overleaf/overleaf/main/services/web/frontend/js/features/source-editor/extensions/visual/atomic-decorations.ts)；[math.ts](https://raw.githubusercontent.com/overleaf/overleaf/main/services/web/frontend/js/features/source-editor/extensions/visual/visual-widgets/math.ts))。这条路线上复制、撤销、协同与 Markdown 往返几乎免费，但要在 widget 里做结构化编辑就得自己接管焦点：CM6 作者 Marijn Haverbeke 指出 `atomicRanges` 没法通知 widget“光标进来了”，需要自己写 transaction filter ([discuss.codemirror #6399](https://discuss.codemirror.net/t/detect-cursor-motion-into-atomicranges-widget/6399))。结构化文档树路线（ProseMirror/Tiptap node view、Lexical `DecoratorNode`、Slate/Plate 的 void 节点、BlockSuite 的 inline delta 属性）以节点为真相，“点击不塌缩”与弹层或就地编辑天然成立，但节点两侧的光标、拖选、嵌套编辑器的撤销与焦点都要自理。ProseMirror 的 footnote 示例给出了嵌套编辑器的标准范式：内层 step 经 `StepMap.offset` 映射到外层，`Mod-z`/`Mod-y` 转交外层以保持单一撤销栈，`stopEvent` 与 `ignoreMutation` 隔离事件 ([footnote example](https://prosemirror.net/examples/footnote/))；Lexical playground 则在退出编辑时才一次性调用 `setEquation` 写回 ([EquationComponent.tsx](https://raw.githubusercontent.com/facebook/lexical/main/packages/lexical-playground/src/nodes/EquationComponent.tsx))；Slate 要求每个元素至少含一个 Text 后代，并在相邻 inline 之间自动插入空文本，好让选区总有落点 ([Slate Normalizing](https://docs.slatejs.org/concepts/11-normalizing))。

### 嵌入 MathLive 的坑高度一致：焦点、选区、输入法、撤销

把 MathLive 嵌进这些框架，遇到的坑高度一致。根问题是焦点：Marijn 在论坛里明确说，浏览器同一时刻只能聚焦一个元素，聚焦 `<math-field>` 就意味着 ProseMirror 失焦，只能用 CSS 模拟视觉焦点 ([discuss.ProseMirror 9021](https://discuss.prosemirror.net/t/focus-issue-on-mathlive-integration-with-prosemirror/9021))。选区上，inline atom 不设 `draggable` 时段首节点的拖选会失效，设了又没法在点击处放置内部光标；Marijn 建议在节点核心 DOM 两侧放没有 `src` 的 `<img>` 作为“buffer zone”，提问者确认有效，但没有贴出最终代码 ([discuss.ProseMirror 8547](https://discuss.prosemirror.net/t/inline-atomic-node-selection-issues-mathlive-integration-with-draggable-property-conflict/8547))。Chromium 里段落内联的 `<math-field>` 会让 ArrowDown 跳到文档末尾 ([#2939](https://github.com/arnog/mathlive/issues/2939))；shadow DOM 会把事件 target 重定向到宿主元素，判断事件来源只能用 `composedPath()`；MathLive 自带撤销栈，与宿主 history 需要协调，`setValue(..., {silenceNotifications: true})` 可以避免回写引起事件回环 ([Interacting guide](https://mathlive.io/mathfield/guides/interacting/))。输入法方面，CM6 光标紧邻 widget 时组字会被 `cm-widgetBuffer` 的重建打断，Marijn 到 2026-07-02 才提交修复 ([discuss.codemirror #9799](https://discuss.codemirror.net/t/ime-input-may-break-when-cursor-is-adjacent-to-widget-due-to-cm-widgetbuffer-reconstruction/9799))；Lexical v0.46.0 集中修了 Safari、Firefox 与韩文输入法的问题，并新增 `setDOMUnmanaged(dom, {captureSelection: true})` 和 open shadow tree 支持 ([lexical v0.46.0](https://newreleases.io/project/github/facebook/lexical/release/v0.46.0))。Obsidian 的“MathLive in Editor Mode”插件把行内焦点保持标为实验性、依赖编辑器内部行为 ([Obsidian Stats](https://www.obsidianstats.com/plugins/mathlive-in-editor-mode))。主流富文本框架的官方公式方案（Tiptap Mathematics、prosemirror-math、Lexical EquationNode、ckeditor5-math）无一例外回避了结构化编辑，只做“LaTeX 源码加渲染”。

### 协同、序列化与性能都跟着真相源走

协同与序列化的粒度同样由真相源决定。Tiptap 的 `latex`、Plate 的 `texExpression`、Lexical 的 `__equation`、BlockSuite 的 `latex` 都把公式存成节点属性，在 Yjs 下属性按 key last-writer-wins ([Yjs Y.XmlElement](https://docs.yjs.dev/api/shared-types/y.xmlelement))，两人同时改一个公式会丢掉一方；prosemirror-math 把源码作为节点文本、CM6 配 y-codemirror.next 用 Y.Text，才能按字符合并 ([y-codemirror.next](https://raw.githubusercontent.com/yjs/y-codemirror.next/main/README.md))。Markdown 边界的事实标准是 remark-math/micromark，但它自己承认数学不属于 CommonMark 或 GFM、Markdown 里没有数学规范，`singleDollarTextMath` 默认开启 ([micromark-extension-math](https://raw.githubusercontent.com/micromark/micromark-extension-math/main/readme.md))；pandoc 要求开 `$` 右侧、闭 `$` 左侧紧邻非空白，且闭 `$` 后不能紧跟数字 ([pandoc Math](https://pandoc.org/demo/example33/8.13-math.html))；GitHub 另有 `` $`...`$ `` 与 ```` ```math ```` 写法 ([GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions))。各家 `$` 规则不一致，是 Markdown 往返的主要风险。剪贴板上的共识是复制出带定界符的 LaTeX，Notion、prosemirror-math 与 Lexical 的 `getTextContent()` 都这么做。

性能取决于渲染库的成本和编辑器是否只渲染可见部分。CM6 只渲染视口加边距 ([CodeMirror Guide](https://codemirror.net/docs/guide/))，而 Marijn 直言 ProseMirror 不做视口化、整个文档都放进 DOM ([discuss.prosemirror #4972](https://discuss.prosemirror.net/t/improving-performance-loading-on-scroll/4972))。一次第三方压测（2024-10，自动输入一小时）中，Lexical 开着 history 约 23 分钟后内存涨到 3.9 GB 崩溃，关掉 history 时为 10–70 MB，ProseMirror 全程 6–18 MB ([Emergence Engineering](https://emergence-engineering.com/blog/lexical-prosemirror-comparison))，这是单一来源。Obsidian 用户报告数学密集的笔记在 Live Preview 里卡到几乎打不了字 ([Obsidian Forum #34140](https://forum.obsidian.md/t/performance-problem-for-math-heavy-notes/34140))，社区插件 MathJax4-for-Obsidian 靠可配置大小的 LRU 公式缓存与防抖缓解 ([MathJax4-for-Obsidian](https://github.com/TheTenth-THU/MathJax4-for-Obsidian))。MathLive 称字体懒加载、延迟到可见时才渲染 ([MathLive](https://github.com/arnog/mathlive))，但数百个常驻 `<math-field>` 的内存与事件开销没有任何实测，笔记据此推断只应在正在编辑的那个公式上挂载它。缓存键必须覆盖所有影响输出的输入（LaTeX、display 模式、宏或 preamble）：Overleaf 的 `eq()` 就比较 preamble，而 KaTeX 共享的 `macros` 对象会被 `\gdef` 修改 ([KaTeX Options](https://katex.org/docs/options))，一条公式里的全局定义可能污染其他公式的缓存。

### 文字转公式与 AI 改写选区都有现成的交互骨架

“选中文字一键变公式”已有稳定实现：Notion 选中后按 `Cmd/Ctrl+Shift+E` 或点格式菜单的 `√x` ([Notion](https://www.notion.com/help/math-equations))，Plate 的 `insertInlineEquation` 不传表达式时默认取选中字符串 ([Plate](https://platejs.org/docs/equation))，Milkdown Crepe 的 `toggleLatexCommand` 还能反向把公式还原成文本 ([command.ts](https://raw.githubusercontent.com/Milkdown/milkdown/main/packages/crepe/src/feature/latex/command.ts))，本质上都是“用 math 节点替换选区”的单个事务。AI 改写选区的交互收敛成三种：选区旁的建议卡片配 Replace、Insert below、Regenerate（Copilot in Word、Notion AI）([Copilot in Word](https://support.microsoft.com/en-us/word/copilot/rewrite-text-with-copilot-in-word)；[Notion AI](https://www.notion.com/help/guides/notion-ai-for-docs))；就地红绿 diff 配 Accept/Reject（Cursor 的 `Cmd+K`、VS Code 的 Keep/Undo、Tiptap AI Toolkit、Plate）([Cursor](https://cursor.com/docs/inline-edit/overview)；[VS Code](https://code.visualstudio.com/docs/copilot/chat/inline-chat))；以及 ghost 建议配单键接受（Apple Math Notes 的 Return、RemNote 的 Tab）。两个实现细节可以直接复用：Tiptap AI Toolkit 的建议是基于装饰、只对当前用户可见的临时 UI ([Tiptap AI Toolkit](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes))，Plate 的 `withAIBatch` 把流式中间步骤合并成一个 history 批次，让 `tf.ai.undo()` 能安全撤回 ([Plate AI](https://platejs.org/docs/ai))；CM6 一侧可以用 MIT 许可的 `@codemirror/merge`（`unifiedMergeView`、`acceptChunk`/`rejectChunk`）([@codemirror/merge](https://raw.githubusercontent.com/codemirror/merge/main/README.md))。但**笔记没有找到任何产品对“公式内部的局部”做 AI 修改的一手实现描述**；Overleaf 的选区 AI 菜单作用于 LaTeX 源码文本，是否特殊处理数学未见说明 ([Overleaf docs](https://docs.overleaf.com/integrations-and-add-ons/ai-features))。

对“复用到自己的学习系统”而言，许可与框架绑定是硬约束。Tiptap Mathematics 于 2025-06 以 MIT 开源 ([Tiptap blog](https://tiptap.dev/blog/release-notes/were-open-sourcing-more-of-tiptap))，Plate、Lexical、Milkdown 是 MIT，其中 Lexical 仍处于 0.x ([Plate](https://github.com/udecode/plate)；[Lexical](https://github.com/facebook/lexical))；BlockSuite 是 MPL 2.0，并自称处于早期阶段 ([BlockSuite](https://github.com/toeverything/blocksuite))；BlockNote 的 AI 包采用 copyleft 许可，商用需要订阅 ([BlockNote AI](https://www.blocknotejs.org/docs/features/ai))。CM6、ProseMirror 与 Tiptap core 是纯 JS，MathLive 是 custom element，BlockSuite 基于 Lit web components，而 Plate 与 Slate 绑定 React——这决定了组件能不能做成框架无关的 Web Component。ProseMirror、CM6 核心包与 Tiptap core 的许可证本轮没有单独核实。

## 让 AI 只出公式靠 schema 约束，越界与否要由宿主判定

### 结构化输出是“不说废话”的可靠机制，但对推理的影响仍有争议

“AI 不说废话、只出公式”最可靠的实现不是在提示词里反复叮嘱，而是**结构化输出（JSON Schema 加受约束解码），再由宿主用渲染器校验**。2026 年的主流接口都支持这一点。Claude 的 `output_config.format`（`json_schema`）已经 GA，官方称通过受约束解码保证输出符合 schema，旧的 `output_format` beta 参数已废弃；它不支持数值范围和字符串长度约束，首次使用某个 schema 有编译延迟、结果缓存 24 小时，修改格式会让该会话的 prompt cache 失效 ([Claude Docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs))。OpenAI 的 `strict: true` 保证匹配 schema，并用 `refusal` 字段暴露拒答 ([OpenAI](https://openai.com/index/introducing-structured-outputs-in-the-api/))；Gemini 的 `response_format` 加 `schema` 在文档里提醒应用端始终要校验取值 ([Gemini](https://ai.google.dev/gemini-api/docs/structured-output))；Chrome 内置 Prompt API 的 `responseConstraint` 也接受 JSON Schema 或正则 ([Prompt API](https://developer.chrome.com/docs/ai/prompt-api))。这里有一个**未解决的争议**：“Let Me Speak Freely?”（EMNLP 2024 Industry）发现格式限制会显著降低推理任务表现、限制越严退化越多，但对分类类任务有利 ([arXiv 2408.02442](https://arxiv.org/abs/2408.02442))；dottxt 发表了反驳文章“Say What You Mean”，笔记没有细读 ([dottxt](https://blog.dottxt.ai/say-what-you-mean.html))，也没有研究在公式转换任务上直接比较结构化与纯文本输出的准确率。笔记提出的折中是在 schema 里把一句话的 `interpretation` 放在 `latex` 之前，给模型留一个极短的“先想后写”槽位。无论采用哪种方式，宿主兜底都不可省：本地实验中，模型多输出的 `$x^2$` 会让 KaTeX 报 `Can't use function '$' in math mode`，`\label` 则报未定义控制序列 ([本地实验，katex 0.18.9](https://www.npmjs.com/package/katex))。

### 公开评测说明任务不简单，中文完全空白

公开评测说明这个任务并不简单，而中文是一片空白。MathSpeech 基准（1,101 条来自 MIT OpenCourseWare 的音频）上，1-shot 提示的 GPT-4o 平均 CER 为 0.390、Gemini-Pro 为 0.400，两个 T5-small 组成的 120M 专用模型为 0.298 ([MathSpeech](https://arxiv.org/html/2412.15655v3))。ICLR 2026 接收的 Speech-to-LaTeX（S2L）发布了 66,000 多条人工标注和 571k 条合成音频（仅英语和俄语），在 MathSpeech 基准上与 MathSpeech 模型相当（两者 CER 都在 28%–30%），在自建的 S2L-equations 上把 CER 从 MathSpeech 的 64% 降到 27%，但在“数学句子识别”基准 S2L-sentences 上公式 CER 仍有 40% ([S2L](https://arxiv.org/abs/2508.03542))；笔记注明其中 SALMONN-13B 一行（17.5%）没有二次核对。文档级的 TeXpert 基准中，9 个 LLM 在 Hard 级的准确率普遍低于 17% ([TeXpert](https://arxiv.org/abs/2506.16990))。**没有找到任何“中文或中英混合非正式文本 → LaTeX”的公开评测**。与用户立场直接相关的一点是，这些评测都用 CER 计分，区分不了语义等价的不同写法；S2L 用 KaTeX 解析器做规范化，也只让 CER 降了约 1% ([S2L html](https://arxiv.org/html/2508.03542))。既然用户接受同一公式的不同写法，自建评测和线上校验就应按结构或数值等价判定，而不是字符串相等。

### 确定性转换器会制造歧义与方言

确定性转换器很快，但不理解自然语言，还会制造新的方言。本地实验中，Compute Engine 0.134.0 把 `sinx/x` 解析成 s·i·n·x 的乘积（i 被当成虚数单位），把 LaTeX 的 `\sin x/x` 和 `\sin(x/x)` 都规范化成 `["Sin",1]`，只有 `\frac{\sin x}{x}` 得到正确结构 ([本地实验，compute-engine 0.134.0](https://www.npmjs.com/package/@cortex-js/compute-engine))。MathLive 的 `convertAsciiMathToLatex('lim_(x->0) sin(x)/x')` 输出 `\lim_{#?\to#?} _{x\to 0}\sin \frac{x}{x}`，残留占位符且作用域变成 sin(x/x)；`int_1^2 (x+1)^2 dx` 产出 KaTeX 不认识的专有宏 `\differentialD`；`x的平方` 与 `sinx/x` 则原样返回 ([本地实验，mathlive 0.110.0](https://www.npmjs.com/package/mathlive))。换句话说，“sinx/x”的歧义在 LaTeX 层同样存在：`\sin x/x` 渲染出来看着没问题，语义解析器却读成 sin(1)。现有产品在歧义上做得很少。Overleaf/Writefull 的 Equation Generator 只有“预览 → Insert / Generate”，提示发往 OpenAI GPT API ([Writefull](https://blog.writefull.com/instantly-generate-tables-and-equations-in-writefull-for-overleaf/))；Bibby AI 自述用微调过的 Gemini 2.5 Pro，却没有公布公式生成的准确率或延迟 ([Bibby AI](https://arxiv.org/html/2602.16432))。最成熟的歧义交互来自 Wolfram|Alpha：API 返回带 `type`、`word`、`template` 的 `assumptions`，界面把最常见的解释放在首位，其余一键切换 ([Wolfram|Alpha API](https://products.wolframalpha.com/api/documentation))。

### 四个校验器对越界构造给出一致信号，但单个都不够

宿主手里有足够多的机器可读信号来复核 AI 输出，但各层宽严不一。下表摘自调研团队的本地交叉实验 ([katex 0.18.9](https://www.npmjs.com/package/katex)；[mathjax 4.1.3](https://www.npmjs.com/package/mathjax)；[mathlive 0.110.0](https://www.npmjs.com/package/mathlive)；[compute-engine 0.134.0](https://www.npmjs.com/package/@cortex-js/compute-engine))：

| 输入 | KaTeX（`throwOnError:true` + `strict` 回调） | MathJax 4（`formatError` 改为抛错） | MathLive `validateLatex` | Compute Engine `ce.parse` |
|---|---|---|---|---|
| `\begin{tikzcd} A \arrow[r] & B \end{tikzcd}` | `ParseError`：No such environment: tikzcd（position 6，length 8） | `TexError` `UnknownEnv` | `unknown-environment`，另报 `\arrow`、`\end` | `unknown-environment`，`isValid=false` |
| `\begin{CD} A @>f>> B \end{CD}` | 通过 | 同步调用要求重试，异步加载后通过 | `unknown-environment` | 未测 |
| `\frac{1}{x`（缺右括号） | 报缺 `}`（position 10） | `MissingCloseBrace` | **返回 `[]`，漏报** | `expected-closing-delimiter` |
| `\qty(\frac{a}{b})`（physics） | Undefined control sequence | **不抛错，输出染红** | `unknown-command` | `unexpected-command` |
| `\xymatrix{A \ar[r] & B}` | Undefined control sequence | `Misplaced &`（误导性） | `unknown-command` | — |
| `\ce{H2O}`（mhchem） | 未定义，需 contrib 扩展 | 异步加载在 Node 下失败，原因未查明 | **返回 `[]`** | — |
| `x的平方` | 通过，但 `strict` 回调报 3 次 `unicodeTextInMathMode` | — | — | — |

四个校验器对 tikz-cd 给出了**一致、可机读**的“未知环境”信号，这是能力边界可以被确定性检测的直接证据。反过来，MathLive 漏报缺括号、MathJax 默认把未知宏染红而不报错、对 xymatrix 给出误导性的 `Misplaced &`，说明任何单一校验器都不够。unified-latex 与 latex-utensils 的解析非常宽容，对缺括号都不报错，但能稳定清点出用了哪些宏和环境、并给出位置，适合做白名单盘点而不是语法裁判 ([unified-latex](https://github.com/siefkenj/unified-latex)；[latex-utensils](https://github.com/tamuratak/latex-utensils))。校验成本可以忽略：预热后 KaTeX 渲染 5 条典型公式合计约 0.22 ms，`validateLatex` 约 0.11 ms，`ce.parse` 约 0.58 ms。

### 能力边界：宿主判定、模型声明、文案与“AI 出错”分开

基于这些信号，笔记推导出一种“宿主判定、模型辅助声明”的边界设计。模型在 JSON 里填 `status: "unsupported"` 和 `requires: ["tikz-cd"]`；宿主用 AST 清点和渲染器错误码独立复核，再查一张“能力注册表”，把结果分为“已支持”“可自动升级到更重的渲染器”“暂不支持、可后续添加”三档；模型的自述只作提示，两者不一致时记日志，用来改进提示。错误可以统一成四类：`syntax`（缺括号、多余的 `$`，先本地自动修复，仍失败再把 `rawMessage` 和 `position` 回传模型重试一次）、`unsupported-construct`（tikzcd、xymatrix、`\SI`，**不重试**）、`renderer-gap`（KaTeX 不支持而 MathJax 支持，例如 `\require{physics}`）、`semantic-warning`（能渲染但语义可疑，例如 `\sin x/x`，或数学模式里出现中文）。注册表还要把“可渲染”和“可编辑”分开标注，因为 `CD` 在 KaTeX 里可渲染、在 MathLive 里不可编辑，`\differentialD` 恰好相反。文案层面，Google PAIR 把这类情况归为 System Limitation，要求尽可能具体地说明系统的限制、给出替代路径并把控制权交还用户 ([PAIR](https://pair.withgoogle.com/chapter/errors-failing/))；Microsoft 的 18 条人机交互准则中，G1（讲清系统能做什么）、G2（讲清做得多好）、G10（拿不准时收窄服务范围）、G11（解释系统为何这样做）都直接对应 ([Microsoft HAX](https://www.microsoft.com/en-us/research/group/customer-insights-research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/))。在视觉和行为上把“能力边界”与“AI 出错”分开（中性信息色、保留原始 LaTeX、不自动重试），正对应用户“不能让人误以为 AI 出错”的要求。需要说明的是，**这类文案对用户信任的影响没有任何 A/B 数据**，PAIR 与 HAX 都是通用指南。

“可以优化但不锁死上限”在技术上意味着越界内容照样原样保存，扩展层装上之后自动升级。以 tikz-cd 为例，至少有四条可以后补的路：浏览器内的 TikZJax，其中 node-tikzjax 的浏览器版 `isomorphic-tikzjax` 支持 tikz-cd、pgfplots、chemfig、circuitikz ([node-tikzjax](https://github.com/prinsss/node-tikzjax))；服务器端真 TeX，直接照搬 org-latex-preview 的批处理、.fmt、伪错误标记与 dvisvgm；Typst 加 fletcher；以及退而求其次的 amscd `CD`，KaTeX 已支持，但只能画水平和竖直箭头 ([KaTeX Supported](https://katex.org/docs/supported))。TikZJax 的首屏体积与单图编译延迟**没有可靠数字**，需要自测。

### 语义核验、模型选择与语音输入

语义核验可以在浏览器里毫秒级完成。本地实验中，Compute Engine 0.134.0 把 `\int_1^2 (x+1)^2\,dx` 和 `\int_{1}^{2}(x+1)^{2}\,\mathrm{d}x` 解析成同一个 MathJSON，并精确求得 `19/3`；`\lim_{x\to 0}\frac{\sin x}{x}` 得 1，`\sum_{k=1}^{10}k^2` 得 385，`cases` 解析为 `Which`、`pmatrix` 解析为 `Matrix`，单次 3–31 ms ([本地实验，compute-engine 0.134.0](https://www.npmjs.com/package/@cortex-js/compute-engine))。这让“模型另外给出期望值（例如 19/3），宿主独立计算并比对”成为第二条校验路径，两条推理路径可以互相印证；但规范化会把歧义写法悄悄算掉，所以核验必须同时比较结构和数值。Compute Engine 仍是 0.x，几乎每天发版（0.131 到 0.134 集中在 2026-09-18 至 09-24），0.131.0 还改变了“符号后跟括号默认解释为函数应用”的规则 ([Compute Engine Changelog](https://mathlive.io/compute-engine/changelog/))。Python 侧的 SymPy `parse_latex`（ANTLR 与 Lark 两种后端）和 Hugging Face 的 Math-Verify 更适合离线给评测集打分 ([SymPy](https://docs.sympy.org/latest/modules/parsing.html)；[Math-Verify](https://github.com/huggingface/Math-Verify))。

这是一个“几十 token 进、几十 token 出”的窄任务，成本几乎可以忽略，体验取决于首 token 延迟和中文理解。按 2026-09-25 抓取的标价（每百万 token 输入/输出），Claude Haiku 4.5 为 $1/$5 ([Claude Pricing](https://platform.claude.com/docs/en/about-claude/pricing))，`gpt-5-nano` 为 $0.05/$0.40 ([OpenAI Pricing](https://developers.openai.com/api/docs/pricing))，`gemini-3.1-flash-lite` 为 $0.25/$1.50 ([Gemini Pricing](https://ai.google.dev/gemini-api/docs/pricing))；按笔记假设的每次约 1,300 个输入 token、120 个输出 token 换算，每千次调用约 $0.11（`gpt-5-nano`）到 $1.90（Haiku 4.5）。延迟数据残缺：Artificial Analysis 页面上首 token 最快的是非推理模式的 Gemini 2.5 Flash-Lite，0.30 s，Haiku 4.5 和 OpenAI nano 系列的数字没有抓到 ([Artificial Analysis](https://artificialanalysis.ai/models))。本地推理方面，WebLLM 论文称可保留同设备原生性能的 80% ([WebLLM](https://arxiv.org/abs/2412.15803))，二手测评给出 Qwen2.5-0.5B 首 token 约 0.5–2 s，中文质量没有公开评测 ([TinyWeights](https://tinyweights.dev/posts/run-llm-in-browser-webllm/))；Chrome 内置的 Gemini Nano **支持的语言只有英、日、西、德、法，不含中文**，还要求 22 GB 可用磁盘和超过 4 GB 的显存（或 16 GB 内存） ([Prompt API](https://developer.chrome.com/docs/ai/prompt-api))。它何时对网页稳定开放，官方文档写 Chrome 138+，一篇二手博客写 Chrome 148 ([pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/3145/gemini-nano-chrome-built-in-ai-client-side-en))，两者**不一致**。

语音输入这一路，宿主拿到的只是纯文本。macOS 听写的数学命令只覆盖 plus sign、equal sign 等少数符号，multiplication sign 输出的是字母 x，会和变量 x 冲突 ([Apple Support](https://support.apple.com/guide/mac-help/commands-for-dictating-text-on-mac-mh40695/mac))；这与 MathSpeech/S2L 的“ASR 后纠错，再转 LaTeX”阶段同构，典型错误包括 sine 被识别成 side，以及“one over x plus two”到底是 1/(x+2) 还是 1/x+2 的作用域歧义 ([MathSpeech](https://arxiv.org/html/2412.15655v3)；[S2L html](https://arxiv.org/html/2508.03542))。中文没有任何口述数学到 LaTeX 的数据集，只能从 TTS 的朗读规则反推读法：阿里云 CosyVoice 把 `\frac{2}{3}` 读作“三分之二”、`\sqrt{9}=3` 读作“根号下九等于三”、`\sin 30^{\circ}` 读作“sine三十度” ([阿里云 CosyVoice](https://help.aliyun.com/zh/isi/developer-reference/cosyvoice-support-for-latex))，讯飞的规则则明确不支持求和、极限与向量 ([讯飞](https://www.xfyun.cn/doc/spark/tts_latex.html))。由此可以看出中文输入的特殊之处：分数先读分母、“根号下 x 加 1”的作用域不清、三角函数常用英文读法、中英混说与字母音译（“艾克斯”“派”），这些都需要在少样本示例和测试集里专门覆盖（笔记推断）。

## 几乎所有产品都存 LaTeX 字符串，分歧在派生什么、如何兜底

### LaTeX 字符串的统治地位来自消费端

存储格式是六个方向里结论最一致的一个：**LaTeX 字符串是生态中唯一被几乎所有渲染器和笔记、学习产品原生消费的格式**，包括 KaTeX、Temml、MathJax、MathLive、MathQuill，以及 Notion、Obsidian、Anki、Jupyter、GitHub、RemNote、Typora、Wikipedia、pandoc ([Notion](https://www.notion.com/help/math-equations)；[Anki Manual](https://docs.ankiweb.net/math.html)；[GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions))。做结构编辑的产品（MathLive、MathQuill、Tiptap 节点）同样把 LaTeX 当持久化值，结构树只活在内存里；例外只有自带排版引擎的 Word（OfficeMath 内存模型加 OMML 文件格式）、Typst 与 Mathcha ([OfficeMath](https://devblogs.microsoft.com/math-in-office/officemath/))。各产品的真实契约其实是“某个 LaTeX 子集”：Notion 是 KaTeX 子集，并且不支持 `align`，官方建议改用 `aligned` ([Notion](https://www.notion.com/help/math-equations))；Wikipedia 用 texvc 白名单把输入限制在安全子集内 ([Extension:Math](https://www.mediawiki.org/wiki/Extension:Math))。同一个渲染器换一个宿主，子集也会不同。

### 树形格式适合做派生物，不适合做真源

树形格式各有硬伤。MathJSON 官方声明它不打算用作任意数学记号的视觉表示，因而不能替代 LaTeX 或 MathML ([MathJSON](https://mathlive.io/math-json/))；Content MathML 的语义子集从未在浏览器中实现 ([MDN](https://developer.mozilla.org/en-US/docs/Web/MathML))。Presentation MathML 的处境在 2023 年后明显改善：Chromium 109 默认启用 Igalia 实现的 MathML Core，至此所有主流浏览器都原生支持 ([Igalia](https://mathml.igalia.com/))，MathML Core 是 2025-06-24 发布的 Candidate Recommendation Snapshot ([W3C](https://www.w3.org/TR/mathml-core/))。但 MathML 4 到 2026-06-04 仍是 Working Draft ([MathML 4](https://www.w3.org/TR/mathml4/))，Interop 2026 的重点领域也不含 MathML ([Interop 2026](https://github.com/web-platform-tests/interop/blob/main/2026/README.md))，Wikipedia 在 2024-10 的分诊中发现 Safari、Firefox、Android Chrome 上的重音、上下标、尺寸与间距问题 ([Native MathML rollout](https://www.mediawiki.org/wiki/Extension:Math/Native_MathML_rollout_%282024%29))。因此 MathML 适合做可靠的**渲染与导出目标**（Typst 0.15、arXiv、Wikipedia 都在往这个方向走），却不适合做真源：它只有呈现、没有宏、冗长，也不便于 AI 生成与改写。

转换工具的保真度有清晰的分界。LaTeX 到 Presentation MathML 的路径成熟且多家实现（Temml、KaTeX、MathJax 4、LaTeXML、pandoc/texmath、WikiTexVC），多数能把原始 TeX 放进 `<annotation encoding="application/x-tex">`，例如 Temml 的 `annotate` 和 LaTeXML 的 `--mathtex` ([Temml](https://temml.org/docs/en/administration)；[latexmlpost](https://math.nist.gov/~BMiller/LaTeXML/manual/commands/latexmlpost.html))；KaTeX 也这样做的证据来自二手来源 ([zatex #119](https://github.com/gregoreesmaa/zatex/issues/119))。规模化数据来自 arXiv：LaTeXML 让约 97% 的投稿产出“某种 HTML”（这是可用性上限，不是质量指标），约 75% 没有 LaTeXML 错误，Rust 重写版快 10–30 倍 ([arXiv:2605.16562](https://arxiv.org/html/2605.16562v1))。反方向和语义方向则明显有损。MathMLben 对 9 个工具的评测发现，多数转换器根本不支持从呈现到内容的转换，支持的也常在基础输入上给出数学上错误的内容表示 ([MathMLben](https://ar5iv.labs.arxiv.org/html/1804.04956))；Compute Engine 会静默恢复（`13^{\text{th}}` 退化为 13、`\cancel{x}` 被解包），canonical 形式还会改变结构（`\frac{7}{-4}` 变成 `["Rational", -7, 4]`），文档没有承诺往返 ([Compute Engine LaTeX Syntax](https://mathlive.io/compute-engine/guides/latex-syntax/))；pandoc 在 texmath 解析失败时回退为原样 TeX 并发出警告 ([pandoc #7771](https://github.com/jgm/pandoc/issues/7771))。按构造归纳，最常丢失的是宏、`\label`/`\ref`/`\tag`、颜色、`\text` 周边、对齐环境、空格命令，以及规范化带来的字面漂移。

### 越界公式的存储有成熟的“源码 + 能力声明 + 回退”模式

对于结构编辑器处理不了的公式，成熟格式都遵循“保存权威源码、声明所需能力、提供回退渲染”的模式。MathML 用 `<semantics>` 配 `<annotation>` 同时携带多种表示 ([MathML 4](https://www.w3.org/TR/mathml4/))；OOXML 的 `mc:AlternateContent` 用 `mc:Choice Requires` 声明读者必须支持的能力，不匹配时使用 `mc:Fallback`，Office 正是这样把公式和回退图片包在一起 ([Open XML SDK](https://learn.microsoft.com/en-us/office/open-xml/general/introduction-to-markup-compatibility))；pandoc 的 raw attribute 只把 ```` ```{=latex} ```` 这类内容直通给匹配的输出格式 ([pandoc raw](https://pandoc.org/demo/example33/8.14-raw-html.html))；ProseMirror 社区用 catch-all 原子节点把外来内容的 `outerHTML` 存为属性、序列化时还原 ([discuss.ProseMirror #8999](https://discuss.prosemirror.net/t/schema-for-preserving-unknown-html-content-and-structure-as-is/8999))。笔记据此推导的公式节点形态是：`source.text` 是唯一权威字段，永远原样保存；`requires` 声明所需的渲染层；`tier` 取 structural、render-only 或 opaque；`fallback`（SVG/MathML 及其生成器版本）只是可丢弃的缓存；`macrosRef` 与派生的 `semantic` 可以随时重算。关键性质是每次加载时按当前能力重算 `tier`：装上新的渲染层后，越界公式自动升级，**不需要迁移数据**，这是“不锁死上限”在存储层的落点。

### 复用到学习系统时，差别只在定界符、子集与宏

复用到学习系统时，差别只在定界符、子集和宏。Anki 用 `\(...\)` 与 `\[...\]`，`$` 与 `$$` 不是它的 MathJax 定界符，本地 LaTeX 生成图片只能在桌面端完成 ([Anki Manual](https://docs.ankiweb.net/math.html))；Markdown 系用 `$…$` 与 `$$…$$`；MyST 能在 frontmatter 的 `math:` 下定义宏并传到 LaTeX 与 Typst 导出，它的 `{math}` 还允许用 `:typst:` 同时给出原生 Typst 写法 ([MyST](https://mystmd.org/guide/math))；pandoc 的 `latex_macros` 只作用于 reader ([pandoc macros](https://pandoc.org/demo/example33/8.15-latex-macros.html))。由此推出的可移植做法（笔记推断）是：存储不带定界符的 LaTeX，导出时按目标加定界符；以 KaTeX 与 MathJax 默认包的交集为“可移植档”，超出部分在节点上标记；学习卡片脱离原文档，导出到 Anki 时用展开宏后的 LaTeX（MathLive 有 `latex-expanded` 格式）或随卡片携带宏表。去重与检索可以用 Compute Engine canonical MathJSON 的哈希，以规范化 LaTeX 兜底；ARQMath 同时用 LaTeX、Symbol Layout Tree 和 Operator Tree 三种表示做公式检索 ([ARQMath 2020](https://www.cs.rit.edu/~dprl/ARQMath/2020/papers/Errata-TableA2-Overview_of_ARQMath_2020.pdf))，一项公式抽取基准称用 LLM 判断语义等价与人工判断的相关系数 r=0.78 ([arXiv:2512.09874](https://arxiv.org/html/2512.09874v1))，这两条都**只来自搜索摘要**。

存储格式与 AI 改写之间还有一个值得正视的张力。EMNLP 2026 的 .tmu 论文认为 TeX 缺乏显式的结构表示，与 LLM 工作流存在架构错配，影响语义生成与错误定位；树结构的 .tmu 在四项 LLM 评测中都优于 .tex，在其上微调的最终训练损失低约 43% ([arXiv:2603.02873](https://arxiv.org/abs/2603.02873))。它研究的是文档而非单个公式，但与“选中公式局部让 AI 改”的需求直接相关。如果真源是 LaTeX 字符串，局部改写更稳妥的做法是借结构层（MathLive 选区，或 MathJSON 子表达式及其 `sourceOffsets`）定位子树对应的字符串片段，只把片段交给模型，再拼回原串重新校验（笔记推断）；如果真源是树，AI 仍然要经过序列化读写，规范化漂移只是换了个位置出现。

## 结论

这次调研最大的收获，是把“存什么”和“编辑时挂什么”拆开来看：主流产品早已这样做，LaTeX 字符串负责可移植，结构树只在编辑时存在。LaTeX 在可移植性上几乎没有对手，MathLive 在结构化交互上几乎没有对手，Typst 在口语化输入和图表同源上有真实优势；但三者之间的每一次往返——MathLive 的重新序列化、Compute Engine 的规范化、Typst 与 LaTeX 的互转——恰恰是证据最薄、漂移最多的地方。所以选型真正的难点不在挑哪个库，而在决定哪一层有权改写用户写下的字面。能力边界同样应该当作宿主的确定性属性来设计：渲染器对未知环境的判断高度一致，模型的自述只是提示；只要源码原样保存、`tier` 在加载时重算，“上限”就由装了哪些渲染层决定，而不是由已经写下的数据决定。

速度问题被高估，集成问题被低估。KaTeX 的同步路径在亚毫秒级，org-latex-preview 的全部技巧只在引入真 TeX 层时才用得上，而且它自己也绕不开秒级防抖；反过来，焦点、选区、中文输入法、双撤销栈这些集成问题，在 ProseMirror、CodeMirror 6、Lexical 与 MathLive 的 issue 里 2025–2026 年仍在被修。决定成败的几个未知数都便宜、可测：MathLive 在所选宿主里的中文输入法表现、Typst WASM 的首载时间、候选模型在中文非正式输入上的准确率、MathLive 在用户自己的公式语料上的往返漂移。它们比任何公开基准都更能回答该走哪条路。

## 需要你拍板的关键设计决策

下面每项决策都列出调研支持的选项与各自的证据，不预设答案。决策之间有依赖：真源若选 Typst，结构化编辑引擎的现成选项几乎归零；宿主框架若选 CodeMirror 6，协同与源码模式几乎免费，就地结构化编辑的成本却会上升。

### 决策一：公式的持久化真源

选项 A 是不带定界符的 LaTeX 字符串加 inline/display 标志，渲染结果、MathML、MathJSON 都作为可重算的派生缓存。这是 Notion、Obsidian、Anki、MathLive 等几乎所有产品的做法，导入导出近乎恒等，AI 生成 LaTeX 的工具与评测也最多；代价是语义弱、各渲染器子集不同、宏难以移植，以及 .tmu 论文指出的 TeX 与 LLM 工作流的结构错配。选项 B 是以 Typst 数学源为真源，LaTeX 只作导入导出（tex2typst、typst2tex、pandoc），换来更接近口语的输入、带 hint 的诊断和 fletcher/cetz 的图表同源；代价是解包约 28 MB 的编译器包、pre-1.0 的破坏性变更、没有保真度基准的有损转换、下游学习系统都要转换，以及没有现成的结构化编辑器。选项 C 是以树（自定义 AST、MathJSON 或类 OMML 模型）为真源，结构编辑与 AI 子树操作更自然；但 MathJSON 官方否认自己能做视觉表示，任何树都要经序列化才能导出，TeXmacs 的经验说明保真的工程代价很高。选项 D 是同一公式并存两种源，MyST 的 `{math}` 允许在 LaTeX 旁用 `:typst:` 给出原生 Typst 写法，这是笔记里唯一的先例，两份源的一致性要自己维护。

### 决策二：编辑器宿主框架

选项 A 是 CodeMirror 6 的“源码加装饰”（Overleaf、Zettlr、Obsidian 的路线）：源码模式、复制和字符级协同几乎免费，视口渲染适合公式密集的长笔记；但结构化编辑必须在 widget 里自理焦点，`atomicRanges` 无法通知 widget，邻接 widget 的输入法问题 2026-07 才修复。选项 B 是 ProseMirror/Tiptap 的 inline atom 节点加 node view：点击不塌缩天然成立，Tiptap Mathematics（MIT）和 prosemirror-math 可作起点，footnote 示例给出嵌套编辑器的撤销与事件隔离范式；代价是整个文档入 DOM，节点两侧的光标与拖选要用 buffer `<img>` 之类的技巧处理。选项 C 是 Lexical 的 `DecoratorNode`：v0.46 的 `captureSelection` 与输入法修复可能降低嵌入难度，但仍是 0.x，且一次第三方压测里开 history 出现内存暴涨。选项 D 是直接采用 BlockSuite 或 Milkdown Crepe 的现成公式功能，最快，但交互被框架定型为弹层源码编辑，BlockSuite 还是 MPL 2.0 且处于早期。“做成框架无关的 Web Component”这一复用目标，会排除绑定 React 的 Plate 与 Slate，或者至少要求多一层适配。

### 决策三：公式的交互模型与源码切换

选项 A 是就地结构化编辑（C 类）：非编辑态只放静态渲染，点击时在原位挂载 `<math-field>`，用 `mf.position = mf.getOffsetFromPoint(e.clientX, e.clientY)` 把光标直接落到被点的子元素上。选项 B 是原子节点加锚定弹层（B 类，Notion、RemNote、Plate 的模式），弹层里可以放 MathLive，也可以放源码框加实时预览；正文布局更稳定，但“点哪改哪”要多一步。选项 C 是在 A 或 B 之上保留“光标进入即展开源码”（A 类）作为源码模式。源码切换的粒度本身也要选：全局开关（Obsidian 的 Toggle Live Preview/Source mode 是先例）、单个公式在 `<math-field>` 与 CodeMirror/textarea 之间切换，或两者兼有。键盘进出可以组合 Notion/RemNote 的“方向键移到公式即打开”与 MathLive 的 `move-out` 事件来实现。

### 决策四：结构化编辑引擎

选项 A 是锁定版本的上游 MathLive（渲染不可信内容须 0.110.0 以上），接受每半年一次的破坏性大版本、单人维护，以及尚未解决的输入法与无障碍问题。选项 B 是维护自己的 MathLive fork，或评估 `@lofcz/mathlive` 等第三方 fork（同时避开 `mathlive-tera` 这种版本号高于上游的包），便于自带输入法与序列化补丁，代价是长期的合并成本。选项 C 是 Desmos fork 的 MathQuill：有受 MathSpeak 启发的读屏支持，但没有发布到 npm、没有区间选区 API、遇到未知命令整体失败。选项 D 是自研“LaTeX 真源加带源码区间的 atom 树、只重写被改动区间”的编辑器，这是 TeXmacs conservative conversion 与 MathLive `verbatimLatex` 思路的推广，控制力最强，但笔记没有找到现成实现。选项 E 是不做结构化编辑、只用弹层源码编辑，它不满足“点下标里的 0 直接改”，只能作为不可结构化编辑的公式的降级路径。

### 决策五：序列化漂移的容忍度

选项 A 是接受 MathLive 的重新序列化，每次结构编辑后直接写回 `getValue('latex')`，最简单，但会出现 `\frac{1}{2}` 变成 `\frac12` 这类字面变化，并随 MathLive 版本漂移。选项 B 是“未改动的公式字节不变、只有发生结构编辑才写回”，保存时自检 `serialize(parse(s)) === s`，不相等就保留原串。选项 C 是只把被改动子树对应的源码区间拼回原串，需要自研带 span 的解析器，因为 MathLive 没有公开字符偏移映射。选项 D 是统一过一遍自有 serializer 做规范化，或者等 #3055 的 `compactSerialization` 合并后固定拼写。这一决策同时决定了 AI 局部改写结果的回写方式。

### 决策六：渲染栈与分层

第一层的候选有 KaTeX（HTML 输出，约 76 KB gzip，`ParseError` 带位置，默认抛错）、Temml（MathML 输出，约 50 KB gzip，质量随浏览器，默认不抛错）、MathLive 静态渲染（`<math-span>` 或 `mathlive/ssr`，与编辑态外观一致但体积大）以及 Typst SVG（typst.ts，体积大，需在 worker 中常驻）；静态层与编辑层用不同引擎时，进入编辑态可能出现细微的布局跳动（笔记推断）。第二层可以是懒加载的 MathJax 4（约 281 KB gzip，补上 physics、bussproofs、`\label` 等，但必须去掉 `noundefined` 或检测染红的输出），也可以不设。第三层面向图表与真 TeX，候选有浏览器内的 TikZJax/node-tikzjax、busytex（约 32 MB WASM 加 90–400 MB 数据）、照搬 org-latex-preview 的服务器 TeX（批处理 preview 页、mylatexformat .fmt、`auctex` 伪错误标记、dvisvgm、sha1 缓存），以及 Typst 加 fletcher/cetz。要决定的是首版装哪几层、哪些只在注册表里标为“planned”，以及各层缓存键包含哪些字段（引擎版本、宏表、源码、display 模式、主题色）。

### 决策七：能力边界的判定、存储与呈现

判定权上，选项 A 是以宿主注册表（AST 清点加多个渲染器错误码）为准，模型的 `requires` 只作提示；选项 B 是信任模型自述；选项 C 是只看第一层渲染器是否报错。本地实验支持 A 的可行性（四个校验器对 tikz-cd 一致），也显示单一校验器会漏报或误导。存储上，越界内容可以作为 opaque 节点原样保存源码并附可丢弃的回退缓存（类似 OOXML 的 `mc:AlternateContent`），也可以拒绝插入；前者让“装上新渲染层即自动升级”成为可能。呈现上需要决定：tier 的粒度（structural、render-only、opaque，外加“可渲染不等于可编辑”）；文案（PAIR 的“具体说明限制、给出替代路径、交还控制”，HAX 的 G1、G2、G10、G11）；视觉上是否与“AI 出错”区分；边界类错误是否自动重试（笔记的建议是不重试）；以及是否主动提供 amscd `CD` 这类简化替代。

### 决策八：AI 调用契约、生成目标与歧义处理

输出形式上，选项 A 是把各家结构化输出（Claude `output_config.format`、OpenAI `strict`、Gemini `response_format`、Prompt API `responseConstraint`）映射到同一个 schema，笔记草拟的字段有 `status`、`interpretation`、`latex`、`alternatives`、`requires`、`confidence`、`check`、`notes`，全部用字符串或 enum，以兼容 Claude 不支持数值约束；选项 B 是“只输出一行公式”加 stop sequence，由宿主剥掉 `$`、`\[` 和代码围栏，适合不支持结构化输出的本地模型。生成目标语言可以是 LaTeX（配合 KaTeX 子集白名单，并禁用 `\label` 与定界符），也可以是 Typst（配合预定义算符表与符号名表，减少 `unknown variable`），这与决策一联动。歧义处理可以是 Wolfram 式的假设标签一键切换、弹窗追问，或静默取最常见的解释并在 `notes` 里说明。语义核验可以是模型另给期望值、由 Compute Engine 独立计算比对，也可以是结构核验、两者兼有或不做。是否在 AI 返回前先显示确定性预览（AsciiMath 转换或 UnicodeMath 式 autobuildup）也要决定；本地实验显示这类转换会产出 `\differentialD` 和 `#?` 残留，必须走同一条校验管线。

### 决策九：模型部署、触发方式与语音输入

部署上，选项 A 是托管的非推理小模型（按 2026-09 标价每千次调用约 $0.1–$2，已知最快的首 token 约 0.3 s，但 Haiku、nano 系列的延迟需自测）；选项 B 是为选区改写与长上下文升级到中档模型；选项 C 是浏览器本地的 WebGPU 小模型（WebLLM、Transformers.js），可以离线，但中文质量没有评测，可能需要用 S2L 数据加自建中文样本微调；选项 D 是 Chrome 内置的 Gemini Nano，不支持中文且硬件门槛高。触发方式可以是显式触发（回车、Tab、按钮、听写结束），也可以边打边转（笔记建议 150–300 ms 防抖，并用 AbortController 取消过期请求）。语音方面，可以直接消费系统听写的纯文本，在提示中声明同音误识别与中文读法（分母先读、“根号下”的作用域）；也可以自接 ASR（例如浏览器内的 Whisper，参照 S2L 的“ASR 加 LLM 纠错”管线）。为了可复用，注入函数的接口也要定下来，笔记给出的 provider-neutral 形态是 `(req: {text, mode, selection?, context?, target}) => Promise<FormulaResult>`。

### 决策十：选区局部改写与“文字转公式”的协议

改写协议上，选项 A 是把整条公式发给模型，选区用 `⟦` `⟧` 这类 LaTeX 中不会出现的标记包住，要求同时返回 `replacement` 与 `full_formula`，宿主校验选区外的前后缀没有变，类似 Aider 的 SEARCH 块必须精确匹配 ([Aider](https://aider.chat/docs/more/edit-formats.html))；选项 B 是只返回完整的新公式；选项 C 是 search/replace 式只返回差异。选区可以先扩展到最近的完整子树（借助 MathLive 选区或 unified-latex AST），也可以按原始字符区间发送。预览可以是渲染前后对比加改动高亮，源码层用 `@codemirror/merge` 的 `unifiedMergeView`；建议可以是只对本地可见的装饰（Tiptap 的做法），也可以是持久的 suggestion marks（BlockNote 的 prosemirror-suggest-changes）([npm](https://www.npmjs.com/package/@blocknote/prosemirror-suggest-changes))；撤销可以仿照 Plate 的 `withAIBatch` 合并为一步。批注可以存成“公式节点加 LaTeX 字符偏移区间”的旁注数据，也可以写进 LaTeX（例如 MathLive `applyStyle` 的颜色），后者可能污染源码（笔记注明未验证）。“选中文字变公式”则可以直接把选中文本当 LaTeX 包成公式并立即打开编辑器（Notion、Plate、Milkdown 的做法），也可以先经 AI 规范化（RemNote 的 Tab 接受）；是否提供 Milkdown 那样的反向命令也在此决定。

### 决策十一：撤销与协同粒度

撤销上，选项 A 是把一次公式编辑会话合并为宿主 history 的一步（Lexical 在退出时一次 `setEquation`，或编辑中用 `setNodeMarkup` 并设 `addToHistory: false`、会话结束再提交），会话内的逐键撤销交给 MathLive 自己的 history；选项 B 是把 MathLive 的每次 `input` 都写进宿主 history；选项 C 是像 ProseMirror footnote 示例那样，把内层的 `Mod-z` 转交外层以维持单一撤销栈。协同上，公式存为节点属性意味着 Yjs 下整条 last-writer-wins，存为节点文本或 Y.Text 则可以字符级合并；对个人学习系统，前者可能够用（笔记推断），但将来若要多人共享笔记，这个选择很难事后更改。

### 决策十二：宏、记号一致性与导出

宏可以完全不支持，也可以设笔记级或库级宏表，让 KaTeX 的 `macros`、MathLive 的 `mf.macros` 与 `validateLatex({macros})` 共用同一份定义，并把宏表纳入渲染缓存键。导出时，宏可以展开（MathLive 的 `latex-expanded`）后写进 Anki 卡片这类脱离原文的单元，也可以随文档携带（MyST frontmatter 的做法）。定界符要按目标决定：Anki 用 `\(...\)`/`\[...\]`，Markdown 用 `$`/`$$`，与 GitHub 语法冲突时可用 `` $`…`$ ``。此外还要决定：是否以 KaTeX 与 MathJax 的交集为“可移植档”并对超出部分告警（例如导出到 Notion 时把 `align` 改成 `aligned`）；HTML 导出是否写 MathML 加 TeX annotation；去重键用 canonical MathJSON 哈希、规范化 LaTeX，还是两者组合；以及给 AI 的上下文里是否附带本页已用记号（`\mathrm{d}` 还是 `d`，`\vec` 还是 `\mathbf`），让模型沿用同一套写法。
